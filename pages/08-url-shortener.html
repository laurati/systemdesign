Projete um encurtador de URL

O "hello world" do system design, pedido em entrevistas de todos os níveis. Simples na superfície, mas com decisões ótimas para discutir: geração do código, redirecionamento, cache e escala de leitura.

Ao final você saberá:

  • Estimar escrita, leitura e armazenamento e derivar o tamanho do código curto.
  • Comparar hash + resolução de colisão × ID único + base62.
  • Escolher entre 301 e 302.
  • Implementar base62 e o serviço em Go.

Requisitos

Pode dar um exemplo?

https://www.systeminterview.com/q=chatsystem&c=loggedin&v=v3&l=long vira https://tinyurl.com/y7keocwj, e clicar no curto redireciona para o longo.

Volume?

100 milhões de URLs geradas por dia.

Quão curto?

O mais curto possível.

Quais caracteres?

Números e letras: [0-9a-zA-Z].

Pode apagar ou atualizar?

Para simplificar, não.

  • Funcionais: encurtar e redirecionar.
  • Não funcionais: alta disponibilidade, escalabilidade, tolerância a falhas; redirecionamento com baixa latência.

Estimativas

  • Escritas: 100 M/dia ÷ 105 ≈ 1.160/s.
  • Leituras (assumindo 10:1): 11.600/s.
  • Em 10 anos: 100 M × 365 × 10 = 365 bilhões de registros.
  • URL média de 100 bytes, então 365 bi × 100 B ≈ 36,5 TB.

Tamanho do código: com 62 caracteres, precisamos de 62n ≥ 365 bilhões. 626 ≈ 56,8 bilhões (pouco); 627 ≈ 3,5 trilhões. Então n = 7.

Design de alto nível

A tabela é simples: (id PK, short_url UNIQUE, long_url, created_at), mais um índice em long_url (ou no hash dela) para devolver o mesmo código se a URL já existir.

Deep dive: gerar o código curto

Opção A: hash + resolução de colisão

Aplicar CRC32, MD5 ou SHA-1 à URL longa e pegar os 7 primeiros caracteres. Mas 7 caracteres de um hash colidem. Solução: se colidir, concatenar um sufixo predefinido à URL e refazer o hash até não colidir.

  • Cada geração exige consultar o banco para ver se o código existe, o que é caro. Um Bloom filter acelera a checagem.
  • Vantagem: a mesma URL gera o mesmo código naturalmente; não precisa de gerador de IDs.

Opção B: ID único + conversão base62

Gere um ID numérico único (Snowflake, contador distribuído ou faixas de IDs pré-alocadas) e converta para base62. Exemplo: 11157 = 2×62² + 55×62 + 59, que vira "2" "T" "X" = 2TX.

Escolha comumID + base62. Para não ser adivinhável, embaralhe o ID com uma permutação reversível (por exemplo, uma pequena cifra de Feistel ou multiplicação por um inverso modular) antes da conversão, ou use um Snowflake, cujos IDs não são consecutivos.

Fluxo de encurtamento

  1. Recebe a URL longa.
  2. Ela já está no banco? Devolve o código existente.
  3. Senão, gera um ID único, converte para base62 e grava (id, short, long).
go/shortener/shortener.go
// Package shortener implementa um encurtador de URL usando
// "ID único + conversão base62" — a abordagem sem colisões.
//
// Fluxo de escrita:  longURL → já existe? devolve o short → senão gera ID
// único (ex.: Snowflake ou contador distribuído) → base62(ID) → salva.
// Fluxo de leitura:  GET /{short} → cache → banco → 301/302 para longURL.
package shortener

import (
	"errors"
	"net/http"
	"strings"
	"sync"
)

const alphabet = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

// Encode converte um inteiro para base62. 62^7 ≈ 3,5 trilhões de URLs com 7 chars.
func Encode(n uint64) string {
	if n == 0 {
		return string(alphabet[0])
	}
	var b [11]byte // 62^11 > 2^64
	i := len(b)
	for n > 0 {
		i--
		b[i] = alphabet[n%62]
		n /= 62
	}
	return string(b[i:])
}

func Decode(s string) (uint64, error) {
	var n uint64
	for _, c := range s {
		idx := strings.IndexRune(alphabet, c)
		if idx < 0 {
			return 0, errors.New("caractere inválido em base62")
		}
		n = n*62 + uint64(idx)
	}
	return n, nil
}

// IDGenerator abstrai o gerador de IDs únicos (Snowflake, ticket server, range de IDs…).
type IDGenerator interface{ Next() (int64, error) }

// Service guarda os mapeamentos. Em produção: tabela (id, short, long) em
// um banco + cache (Redis) na frente para as leituras (read-heavy ~100:1).
type Service struct {
	mu      sync.RWMutex
	ids     IDGenerator
	byShort map[string]string
	byLong  map[string]string // índice para não duplicar a mesma URL longa
}

func NewService(ids IDGenerator) *Service {
	return &Service{ids: ids, byShort: map[string]string{}, byLong: map[string]string{}}
}

func (s *Service) Shorten(long string) (string, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if short, ok := s.byLong[long]; ok {
		return short, nil
	}
	id, err := s.ids.Next()
	if err != nil {
		return "", err
	}
	short := Encode(uint64(id))
	s.byShort[short] = long
	s.byLong[long] = short
	return short, nil
}

func (s *Service) Resolve(short string) (string, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	long, ok := s.byShort[short]
	return long, ok
}

// ServeHTTP faz o redirecionamento.
//   - 301 (Moved Permanently): o navegador cacheia; menos carga, mas você perde analytics.
//   - 302 (Found): toda visita passa pelo serviço; permite contar cliques.
func (s *Service) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	long, ok := s.Resolve(strings.TrimPrefix(r.URL.Path, "/"))
	if !ok {
		http.NotFound(w, r)
		return
	}
	http.Redirect(w, r, long, http.StatusFound)
}

Deep dive: redirecionamento em escala

  • Leitura muito maior que escrita: cache short → long no Redis. Com 20% das URLs gerando 80% do tráfego, um cache de algumas dezenas de GB dá um hit rate altíssimo.
  • Dados imutáveis (sem update), então o cache nunca fica inconsistente. TTL longo e LRU.
  • Banco: 36 TB e acesso por chave pedem um KV/NoSQL particionado por short_url (DynamoDB, Cassandra) ou um relacional sharded. Réplicas para leitura.
  • Latência global: servidores de redirect em várias regiões, com o cache local e replicação assíncrona dos dados (consistência eventual é aceitável: uma URL recém-criada leva alguns segundos para aparecer em outra região, ou cai no fallback para a região de origem).
  • Para 301, o próprio navegador cacheia; respostas de redirect também podem ficar na CDN.

Para o fechamento

  • Rate limiter no POST: evita que um usuário mal-intencionado esgote IDs ou use o serviço para spam.
  • Segurança: checar URLs maliciosas (Google Safe Browsing), página de aviso.
  • Analytics: com 302, publicar eventos de clique no Kafka e agregar em batch/stream.
  • Expiração: TTL por URL e limpeza preguiçosa (na leitura) + job periódico.
  • Códigos personalizados (sho.rt/minha-marca): checar disponibilidade com constraint UNIQUE.

Simulação de entrevista

Por que não simplesmente usar MD5 da URL e pegar 7 caracteres?

Daria certo para começar, e tem a vantagem de que a mesma URL gera o mesmo código sem consultar nada. O problema são as colisões: 7 caracteres base62 de um hash dão ~3,5 trilhões de combinações e vamos guardar 365 bilhões, então pelo paradoxo do aniversário colisões aparecem cedo. Cada escrita precisaria checar o banco e, se colidir, refazer com um sufixo. Prefiro gerar um ID único e converter para base62: zero colisão por construção.

Mas aí você precisa de um gerador de IDs distribuído.

Sim. Escrevemos ~1.200/s, então um esquema simples basta: cada servidor pega uma faixa de 10 mil IDs de um contador central (Redis INCRBY ou uma linha no banco) e a consome localmente. Se o servidor morre, perdemos alguns IDs da faixa, o que é irrelevante. Isso evita depender de um serviço a cada criação.

IDs sequenciais deixam alguém enumerar todas as URLs.

Verdade, e algumas URLs encurtadas são privadas, como documentos compartilhados. Eu passaria o ID por uma permutação bijetiva no espaço de 627, com uma cifra de Feistel e uma chave secreta: continua único e reversível, mas consecutivos não parecem consecutivos.

Onde está o gargalo?

Nas leituras: ~12 mil/s, com picos virais muito maiores numa única URL. O cache Redis resolve a maioria; para uma URL viral, ela vira hot key e eu adicionaria cache local in-process nos web servers com TTL de segundos, ou deixaria a CDN responder o redirect.
