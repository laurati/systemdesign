Projete um sistema de notificações

Push mobile, SMS e e-mail para milhões de usuários: confiável (sem perder nada), sem duplicar, respeitando preferências e limites, e desacoplado de provedores terceiros instáveis.

Ao final você saberá:

  • Explicar como funcionam APNs, FCM, provedores de SMS e de e-mail.
  • Desacoplar o sistema com filas por canal e workers.
  • Garantir entrega (at-least-once) sem duplicar (idempotência).
  • Adicionar templates, preferências, rate limiting, retries e monitoramento.

Como um push chega ao celular, por dentro

Seu servidor não fala diretamente com o celular. Quem mantém a conexão com o aparelho é o sistema operacional:

  1. Registro: ao abrir o app pela primeira vez (e após o usuário permitir notificações), o app pede ao sistema um device token. O iOS o obtém do APNs; o Android, do FCM. Esse token identifica a combinação app + aparelho.
  2. O app envia o token ao seu backend, que o grava associado ao usuário.
  3. O sistema operacional mantém uma única conexão persistente e econômica com o APNs/FCM, compartilhada por todos os apps. Por isso o push não gasta bateria por app.
  4. Envio: seu servidor chama a API do APNs (HTTP/2, autenticado por um token JWT assinado com a chave da sua conta de desenvolvedor) ou do FCM, com o device token e um payload pequeno (até 4 KB no APNs).
  5. O APNs/FCM entrega ao aparelho quando ele estiver conectado. Se estiver desligado, guarda a notificação mais recente por um tempo limitado e entrega depois.

Consequências para o design: tokens mudam e expiram (o app foi reinstalado, o usuário trocou de aparelho), então o backend precisa atualizá-los a cada abertura do app e apagar os que o provedor rejeitar. E o "entregue" do APNs significa "aceito pelo APNs", não "visto pelo usuário": confirmação de leitura exige que o app reporte de volta.

Requisitos

Quais tipos?

Push, SMS e e-mail.

Tempo real?

Soft real-time: o mais rápido possível, mas pode haver um pequeno atraso sob carga.

Dispositivos?

iOS, Android, laptop/desktop.

Quem dispara?

Apps clientes e também agendamentos no servidor.

Usuário pode desativar?

Sim, opt-out por canal.

Volume?

10 milhões de push, 1 milhão de SMS e 5 milhões de e-mails por dia.

Estimativas

  • Total: 16 milhões por dia ≈ ~200/s em média. Parece pouco, e é: a média não é o problema.
  • O problema são os picos. Uma campanha para 50 milhões de usuários que precisa sair em 1 hora exige ~14 mil envios/s; um alerta de "o jogo começou" para 10 milhões que precisa sair em 1 minuto, ~170 mil/s.
  • Os provedores impõem limites: um provedor de SMS pode aceitar algumas centenas por segundo por conta; o de e-mail, alguns milhares. Ou seja, nosso sistema consegue gerar mensagens muito mais rápido do que os provedores conseguem receber.
  • Log de notificações: 16 M/dia × ~500 bytes = 8 GB/dia, ~3 TB/ano. Cabe num banco de escrita intensa com retenção limitada (por exemplo, 90 dias).

O que isso implica: o sistema precisa de filas para absorver picos que são ordens de grandeza acima da média, e de controle de vazão por provedor para não ser bloqueado por eles. A pergunta central do design não é "como enviar rápido", mas "como enviar de forma confiável numa velocidade que o provedor aceite, sem que o urgente fique atrás do volumoso".

Coletando informações de contato

Ao instalar o app ou se cadastrar, o servidor grava os device tokens, o telefone e o e-mail. Um usuário pode ter vários dispositivos.

Primeira versão (e seus problemas)

  • SPOF: um servidor só.
  • Difícil de escalar: tudo (bancos, cache, envio) num lugar só.
  • Gargalo de desempenho: montar HTML e esperar respostas de terceiros é lento; um pico derruba o sistema.

Design melhorado

  1. Um serviço chama a API do servidor de notificação.
  2. O servidor valida, busca dados do usuário (cache/banco), checa preferências e monta o evento a partir de um template.
  3. O evento vai para a fila do canal. Filas separadas isolam falhas: se o provedor de SMS cair, push continua.
  4. Workers consomem e chamam o provedor.
  5. O resultado é registrado no log; falhas voltam para a fila com retry.

Deep dive: confiabilidade

Como não perder notificações?

Persistir antes de confirmar: a notificação é gravada no log/banco e na fila durável. O worker só faz ack na fila depois de enviar com sucesso; se o worker morrer no meio, a mensagem é reentregue (at-least-once).

Exatamente uma vez?

Não dá para garantir com provedores externos (o APNs pode ter entregado e a resposta se perdido). Mas dá para reduzir drasticamente as duplicatas com dedup pelo notification_id: antes de enviar, checa se o ID já foi enviado (Redis SET id NX EX 86400 ou uma tabela com chave única).

go/notification/worker.go: idempotência, retry com backoff exponencial + jitter, DLQ
// Package notification mostra o núcleo confiável de um worker de notificações:
//
//   - idempotência: o mesmo evento (notification_id) nunca é enviado duas vezes,
//     mesmo que a fila entregue a mensagem de novo (at-least-once);
//   - retry com exponential backoff + jitter para falhas transitórias do provedor
//     (APNs, FCM, Twilio, SendGrid);
//   - dead-letter: depois de N tentativas a mensagem vai para análise manual.
package notification

import (
	"context"
	"errors"
	"math/rand/v2"
	"sync"
	"time"
)

type Message struct {
	ID      string // notification_id gerado na origem — chave de idempotência
	UserID  string
	Channel string // "push", "sms", "email"
	Body    string
}

// Provider é o serviço terceiro que efetivamente entrega.
type Provider interface {
	Send(ctx context.Context, m Message) error
}

// ErrPermanent indica que não adianta tentar de novo (token de device inválido, e-mail inexistente).
var ErrPermanent = errors.New("falha permanente")

type Worker struct {
	Provider    Provider
	MaxAttempts int
	BaseDelay   time.Duration
	Sleep       func(time.Duration) // injetável nos testes

	mu         sync.Mutex
	sent       map[string]bool // em produção: Redis SETNX com TTL ou tabela com unique key
	DeadLetter []Message
}

func (w *Worker) Handle(ctx context.Context, m Message) error {
	w.mu.Lock()
	if w.sent == nil {
		w.sent = map[string]bool{}
	}
	if w.sent[m.ID] {
		w.mu.Unlock()
		return nil // duplicata: já entregue, ack e segue
	}
	w.mu.Unlock()

	var err error
	for attempt := 0; attempt < w.MaxAttempts; attempt++ {
		if err = w.Provider.Send(ctx, m); err == nil {
			w.mu.Lock()
			w.sent[m.ID] = true
			w.mu.Unlock()
			return nil
		}
		if errors.Is(err, ErrPermanent) {
			break
		}
		// backoff: base·2^tentativa + jitter (evita "thundering herd" de retries sincronizados)
		backoff := w.BaseDelay << attempt
		jitter := time.Duration(rand.Int64N(int64(w.BaseDelay) + 1))
		w.Sleep(backoff + jitter)
	}
	w.mu.Lock()
	w.DeadLetter = append(w.DeadLetter, m)
	w.mu.Unlock()
	return err
}

E do lado de quem pede a notificação?

O serviço de pedidos grava "pedido enviado" no banco dele e depois chama a API de notificações. Se ele cair entre as duas coisas, o pedido foi atualizado e a notificação nunca foi pedida. Se fizer na ordem inversa, pode notificar algo que não aconteceu. A solução padrão é o transactional outbox:

  1. Na mesma transação que atualiza o pedido, o serviço insere uma linha numa tabela outbox ("notificar pedido A-998 enviado", com um ID único).
  2. Um processo separado lê a outbox (por polling ou CDC, lendo o log do banco), publica na fila de notificações e marca a linha como publicada.
  3. Se ele cair depois de publicar e antes de marcar, publica de novo; o ID único faz o sistema de notificações descartar a repetição.

Assim, ou as duas coisas acontecem, ou nenhuma. Detalhes em Sistemas distribuídos.

O store de dedup, dimensionado

Guardar para sempre todos os IDs já enviados não é necessário: duplicatas acontecem por retries, que ocorrem em minutos ou horas. Um SET notif:{id} 1 NX EX 86400 no Redis (grava só se não existir, expira em 24 h) resolve. Com 16 milhões por dia e ~60 bytes por chave, são ~1 GB.

Mecanismo de retry

  • Falhas transitórias (timeout, 5xx, 429 do provedor): retry com backoff exponencial + jitter.
  • Falhas permanentes (token inválido, e-mail inexistente): não repetir; marcar o device como inválido.
  • Após N tentativas: dead-letter queue e alerta.

Componentes adicionais

  • Templates: formatos pré-definidos com parâmetros; consistência, menos erros e permitem A/B test e localização.
  • Configurações do usuário: checar o opt-in por canal antes de enfileirar.
  • Rate limiting por usuário: excesso de notificações leva o usuário a desativá-las. Por exemplo, no máximo 3 de marketing por dia.
  • Horário silencioso / fuso: agendar marketing para o horário local.
  • Prioridade: filas separadas para transacionais (código 2FA, "pedido saiu") e marketing, para que uma campanha de 10 milhões de e-mails não atrase o código de login.
  • Segurança: só serviços autenticados (appKey/appSecret ou mTLS) podem enviar.
  • Monitoramento: tamanho das filas (se cresce, adicione workers), taxa de erro por provedor.
  • Tracking de eventos: aberto, clicado, entregue; vai para analytics.
  • Fallback de provedor: dois provedores de SMS; se um falha, o circuit breaker troca para o outro.

Controlando a vazão para cada provedor

Os workers de SMS não podem simplesmente consumir a fila o mais rápido possível: se o provedor aceita 500/s e mandamos 5.000/s, recebemos 429 em massa e talvez um bloqueio. Cada pool de workers usa um rate limiter compartilhado por provedor (token bucket no Redis, como no capítulo 04), e a fila acumula o excesso. Com isso, a fila deixa de ser só um buffer e vira o lugar onde "esperar a vez" acontece de forma ordenada.

Horário silencioso e agendamento

"Envie às 9h no fuso de cada usuário" significa que a campanha sai em 24 ondas. Implementação comum: uma tabela de notificações agendadas indexada por horário de envio, e um scheduler que a cada minuto busca as que venceram e as publica na fila. Para volumes grandes, agrupe por "balde" de horário (todas as de 09:00 UTC−3) em vez de linha por usuário. Notificações transacionais ignoram o horário silencioso; as de marketing esperam.

E-mail tem regras próprias

  • Autenticação do domínio (SPF, DKIM, DMARC): sem isso, os e-mails vão para spam.
  • Bounces: endereço inexistente (hard bounce) entra numa lista de supressão e nunca mais recebe. Insistir derruba a reputação do domínio.
  • Reclamações: quando o usuário marca como spam, o provedor avisa por webhook; trate como opt-out imediato.
  • Link de descadastro obrigatório em marketing (e exigido por lei em vários países).
  • Separe domínios ou IPs de envio transacional e de marketing: se a campanha for marcada como spam, os e-mails de redefinição de senha continuam chegando.

Central de notificações dentro do app

Muitos produtos também têm um "sininho" com a lista de notificações, lidas e não lidas. É outro canal: uma tabela (user_id, notification_id, created_at, read) particionada por usuário, um contador de não lidas em cache, e, se o usuário estiver com o app aberto, um envio em tempo real pela conexão WebSocket existente.

Simulação de entrevista

O marketing quer mandar uma campanha para 50 milhões de usuários às 9h. Ao mesmo tempo, códigos 2FA precisam chegar em segundos. Como seu sistema lida com isso?

Separo por prioridade desde a entrada: filas distintas para transacional e para bulk, com pools de workers distintos. O 2FA nunca fica atrás da campanha. Também respeito os rate limits dos provedores: APNs e FCM aceitam muito, mas SMS e e-mail têm cotas, e o envio da campanha é controlado (throttled) para não esgotar a cota que o transacional precisa.

E como você gera 50 milhões de mensagens sem travar o serviço?

A campanha não passa pela API síncrona. Um job de campanha pagina a audiência (segmento pré-computado) e publica em lotes na fila bulk; workers expandem para cada device do usuário, aplicam preferências e o limite de frequência, e enviam. Se quisermos "às 9h no fuso de cada usuário", o job agenda os lotes por fuso.

Um worker caiu depois de enviar, mas antes do ack. O que acontece?

A fila reentrega e outro worker pega. Antes de enviar, ele checa o notification_id no store de dedup; como foi gravado após o envio, a segunda tentativa é descartada. Se o crash for exatamente entre o envio e a gravação do dedup, a duplicata é possível, e isso é aceitável para push: garantimos "pelo menos uma vez, quase sempre exatamente uma".

Como saber se está funcionando?

Métricas por canal: profundidade e idade da mensagem mais antiga em cada fila, latência de envio, taxa de erro por provedor e por código, tamanho da DLQ. Alertas na idade da fila transacional. E tracking de entrega e abertura para o produto.
