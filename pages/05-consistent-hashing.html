Projete consistent hashing

A técnica que permite adicionar ou remover servidores de um cluster movendo só uma pequena fração dos dados. Está por trás de Dynamo, Cassandra, CDNs, load balancers e caches distribuídos.

Ao final você saberá:

  • Explicar por que hash % N falha quando o cluster muda.
  • Desenhar o anel de hash e localizar o servidor de uma chave.
  • Usar nós virtuais para equilibrar a carga.
  • Implementar o anel em Go e medir quantas chaves se movem.

O problema do rehash

Com N servidores de cache, a forma ingênua é servidor = hash(chave) % N. Funciona bem enquanto N é fixo. Mas se um servidor cai (N=4 → 3) ou entra um novo (4 → 5), quase todas as chaves mudam de servidor: uma tempestade de cache misses que derruba o banco.

O anel de hash

  1. Pegue uma função de hash com espaço de saída grande (por exemplo, 0 a 232−1, ou SHA-1 com 2160) e "dobre" esse espaço num anel.
  2. Aplique o hash ao identificador de cada servidor (IP ou nome) e posicione-o no anel.
  3. Aplique o hash a cada chave e posicione-a no anel.
  4. A chave pertence ao primeiro servidor encontrado andando no sentido horário.
  • Adicionar s4 entre s3 e s0: só as chaves entre s3 e s4 (antes de s0) mudam, e vão para s4.
  • Remover s1: só as chaves entre s0 e s1 mudam, e vão para s2.

Dois problemas da abordagem básica

  1. Partições de tamanhos desiguais: com poucos servidores, o espaço entre eles no anel é aleatório. Um servidor pode ficar com 40% do anel e outro com 5%.
  2. Distribuição desigual de chaves, e quando um servidor sai, toda a carga dele cai num único vizinho.

Nos testes: com 1 posição por servidor e 4 servidores, um ficou com 86 chaves e outro com 39.191 (de 40 mil).

Nós virtuais (vnodes)

Cada servidor físico aparece várias vezes no anel (s0#0, s0#1, …, s0#199). Cada servidor fica com muitos trechos pequenos espalhados.

  • A distribuição fica uniforme: o desvio padrão cai de forma marcante com 100–200 vnodes (5–10% de desvio). Nos testes, com 200 vnodes: entre 9.313 e 11.036 chaves por servidor.
  • Quando um servidor sai, a carga dele se espalha por vários vizinhos, não por um só.
  • Heterogeneidade: um servidor com o dobro de capacidade recebe o dobro de vnodes.
  • Custo: mais memória para o índice (lista ordenada de posições) e um pouco mais de trabalho para rebalancear.

Implementação em Go

O anel é uma lista ordenada de posições; a busca usa busca binária (O(log V), em que V = total de vnodes), com wrap-around no fim.

go/consistenthash/ring.go
// Package consistenthash implementa um anel de hash consistente com nós virtuais.
//
// Ideia: servidores e chaves são mapeados para o mesmo espaço de hash (um anel
// de 0 a 2^32-1). Uma chave pertence ao primeiro servidor encontrado andando
// no sentido horário. Ao adicionar/remover um servidor, só as chaves do trecho
// vizinho mudam de dono (~K/N chaves), em vez de quase todas (hash % N).
package consistenthash

import (
	"hash/crc32"
	"slices"
	"strconv"
	"sync"
)

type Ring struct {
	mu       sync.RWMutex
	replicas int               // nós virtuais por servidor
	hashes   []uint32          // posições ordenadas no anel
	owner    map[uint32]string // posição -> servidor físico
}

// New cria um anel. Mais réplicas virtuais = distribuição mais uniforme
// (desvio padrão menor), ao custo de mais memória para o índice.
func New(replicas int) *Ring {
	return &Ring{replicas: replicas, owner: map[uint32]string{}}
}

func hashKey(s string) uint32 { return crc32.ChecksumIEEE([]byte(s)) }

func (r *Ring) Add(servers ...string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	for _, s := range servers {
		for i := 0; i < r.replicas; i++ {
			h := hashKey(s + "#" + strconv.Itoa(i))
			r.owner[h] = s
			r.hashes = append(r.hashes, h)
		}
	}
	slices.Sort(r.hashes)
}

func (r *Ring) Remove(server string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	kept := r.hashes[:0]
	for _, h := range r.hashes {
		if r.owner[h] == server {
			delete(r.owner, h)
			continue
		}
		kept = append(kept, h)
	}
	r.hashes = kept
}

// Get devolve o servidor responsável pela chave.
func (r *Ring) Get(key string) string {
	r.mu.RLock()
	defer r.mu.RUnlock()
	if len(r.hashes) == 0 {
		return ""
	}
	return r.owner[r.hashes[r.search(hashKey(key))]]
}

// GetN devolve os N primeiros servidores *distintos* no sentido horário —
// é assim que Dynamo/Cassandra escolhem as réplicas de uma chave.
func (r *Ring) GetN(key string, n int) []string {
	r.mu.RLock()
	defer r.mu.RUnlock()
	var out []string
	seen := map[string]bool{}
	start := r.search(hashKey(key))
	for i := 0; i < len(r.hashes) && len(out) < n; i++ {
		s := r.owner[r.hashes[(start+i)%len(r.hashes)]]
		if !seen[s] {
			seen[s] = true
			out = append(out, s)
		}
	}
	return out
}

// search faz busca binária pela primeira posição >= h (com wrap-around).
func (r *Ring) search(h uint32) int {
	i, _ := slices.BinarySearch(r.hashes, h)
	if i == len(r.hashes) {
		i = 0 // passou do fim: volta ao início do anel
	}
	return i
}
go/consistenthash/ring_test.go (trecho): medindo o remapeamento
func TestMinimalRemapping(t *testing.T) {
	r := New(200)
	r.Add("s0", "s1", "s2", "s3")
	ks := keys(20000)
	before := map[string]string{}
	for _, k := range ks {
		before[k] = r.Get(k)
	}

	r.Add("s4")
	moved := 0
	for _, k := range ks {
		now := r.Get(k)
		if now != before[k] {
			moved++
			if now != "s4" {
				t.Fatalf("chave %s mudou para %s — só deveria ir para o novo nó", k, now)
			}
		}
	}
	// Esperado ~1/5 das chaves. Com hash % N seriam ~80%.
	frac := float64(moved) / float64(len(ks))
	if frac < 0.12 || frac > 0.28 {
		t.Fatalf("fração movida %.2f fora do esperado (~0.20)", frac)
	}
	t.Logf("adicionar 1 nó a 4 moveu %.1f%% das chaves", frac*100)
}

Replicação no anel

GetN(key, 3) anda no sentido horário e pega os 3 primeiros servidores físicos distintos. É assim que Dynamo e Cassandra escolhem as réplicas (a "preference list"). Pular vnodes do mesmo servidor físico é essencial; em multi-DC, também se escolhem réplicas em racks/DCs diferentes.

Onde é usado

  • Amazon Dynamo / DynamoDB, Apache Cassandra: particionamento de dados.
  • Discord: distribuir guilds/conexões entre nós.
  • Akamai e outras CDNs: escolher o servidor de cache para uma URL.
  • Load balancers L4 (Google Maglev): afinidade de conexões com remapeamento mínimo.
  • Clientes de memcached (ketama): distribuição de chaves entre nós de cache.

Simulação de entrevista

Temos um cluster de cache com 20 nós e queremos crescer para 30 sem derrubar o banco. Como distribuir as chaves?

Se hoje for hash % 20, migrar para 30 invalidaria cerca de 2/3 do cache de uma vez e o banco receberia todas essas leituras. Eu usaria consistent hashing: cada nó com algumas centenas de vnodes num anel; a chave vai para o primeiro vnode no sentido horário.

E quanto do cache se perde ao adicionar os 10 nós?

Cerca de 10/30, um terço das chaves, que passa a pertencer aos nós novos. E dá para adicionar os nós um a um, com intervalo entre eles, para que o banco absorva ~3% de misses de cada vez. Também dá para fazer warm-up: os nós novos buscam no nó antigo antes de ir ao banco.

Por que vnodes?

Com uma posição por nó, os trechos do anel ficam de tamanhos aleatórios e alguns nós recebem várias vezes mais carga. Com vnodes, cada nó tem muitos trechos pequenos e a carga converge para a média. Também permitem dar mais vnodes a máquinas maiores, e quando um nó cai, sua carga se divide entre muitos vizinhos.

E uma chave muito quente?

Consistent hashing não resolve hot keys, só distribuição de chaves. Para uma chave quente eu replicaria em vários nós (sufixos key#1..k com leitura aleatória) ou usaria cache local na aplicação com TTL curto.

Quiz

Com consistent hashing e N servidores, adicionar um servidor move aproximadamente:
Só as chaves do trecho do anel assumido pelo novo servidor.
Para que servem os nós virtuais?
Muitas posições por servidor deixam as partições de tamanho semelhante.
Como encontrar o servidor de uma chave no anel de forma eficiente?
O(log V), com wrap-around para o início quando passar do fim.
