Projete um sistema de chat

WhatsApp, Messenger, Slack, Discord. Conexões persistentes com milhões de usuários, mensagens em ordem, sincronização entre dispositivos e o indicador "online".

Ao final você saberá:

  • Comparar polling, long polling e WebSocket.
  • Separar serviços stateless, stateful (chat) e de terceiros (push).
  • Escolher o armazenamento de mensagens e o esquema de IDs.
  • Rotear mensagens 1:1 e de grupo, sincronizar dispositivos e implementar presença.

Conceitos deste capítulo

ConceitoDefinição
PollingO cliente pergunta ao servidor, em intervalos fixos, se há novidades.
Long pollingO cliente faz uma requisição que o servidor só responde quando há novidade (ou após um timeout), e então o cliente pergunta de novo.
WebSocketConexão TCP persistente e bidirecional, iniciada por um upgrade de HTTP.
Serviço statefulServiço que mantém estado por cliente (aqui, a conexão aberta); o cliente fica ligado a uma instância específica.
Service discoveryComponente que diz a qual servidor o cliente deve se conectar, conforme localização, capacidade e saúde (por exemplo, ZooKeeper).
Fila de sincronização (inbox)Fila por destinatário onde caem as mensagens que ele ainda precisa receber.
cur_max_message_idO último ID de mensagem que um dispositivo já tem; ao reconectar, ele pede tudo depois disso.
PresençaIndicador de online/offline de um usuário.
HeartbeatSinal periódico de "estou vivo" enviado pelo cliente; a ausência dele por um tempo indica desconexão.

Como o servidor envia mensagens ao cliente?

O remetente envia via HTTP sem problema. O desafio é o servidor iniciar o envio ao destinatário.

TécnicaComoProblema
PollingCliente pergunta "tem novidade?" periodicamenteA maioria das respostas é vazia: desperdício
Long pollingCliente segura a conexão até haver mensagem ou timeoutO servidor que recebeu a mensagem pode não ser o que segura a conexão; não sabe bem se o cliente desconectou; ainda ineficiente para usuários pouco ativos
WebSocketConexão bidirecional persistente, iniciada como HTTP (upgrade)Conexões stateful: exige gestão eficiente no servidor

Escolha: WebSocket para enviar e receber. Funciona nas portas 80/443, então passa por firewalls.

Como o WebSocket funciona

Ele começa como uma requisição HTTP comum que pede para "trocar de protocolo":

GET /chat HTTP/1.1
Host: chat.exemplo.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Depois do 101, a mesma conexão TCP passa a carregar frames nos dois sentidos, sem cabeçalhos HTTP a cada mensagem (overhead de 2 a 14 bytes por frame). Frames de ping/pong mantêm a conexão viva através de NATs e proxies, que costumam derrubar conexões ociosas depois de alguns minutos.

O ponto que importa para o design: a conexão prende o usuário a um servidor específico. Esse servidor é o único que consegue empurrar dados para aquele usuário. Por isso os chat servers são stateful, e todo o resto do design gira em torno de "como uma mensagem chega ao servidor certo".

E Server-Sent Events (SSE)? SSE é uma alternativa mais simples: uma resposta HTTP que nunca termina, pela qual o servidor envia eventos. É só servidor → cliente; o cliente envia por requisições HTTP normais. Serve bem para notificações, placares ao vivo e streaming de respostas de LLMs. Para chat, em que os dois lados enviam com frequência, WebSocket é o padrão.

Design de alto nível

  • Serviços stateless: login, cadastro, perfil, grupos, atrás de LB. Inclui o service discovery, que indica a qual chat server o cliente deve conectar (por geografia e carga).
  • Serviços stateful: os chat servers mantêm conexões WebSocket. O cliente fica conectado ao mesmo servidor enquanto ele estiver de pé.
  • Terceiros: push notifications para quem está offline.

Escala: 50 M DAU, com ~10 KB de memória por conexão, dá 500 GB. Até caberia num servidor enorme, mas seria um SPOF. Distribuímos entre muitos chat servers.

Armazenamento

Dados genéricos (usuários, settings, grupos, amigos) ficam em relacional com réplicas. Histórico de mensagens é diferente:

  • Volume enorme: o Facebook Messenger e o WhatsApp processam 60 bilhões de mensagens por dia.
  • Só as mensagens recentes são acessadas com frequência.
  • Há acesso aleatório (busca, menções, pular para uma mensagem).
  • Leitura e escrita na proporção de ~1:1.

Escolha: key-value / wide-column (HBase no Messenger, Cassandra e depois ScyllaDB no Discord): escala horizontal e baixa latência; relacionais sofrem com índices enormes e acesso aleatório em larga escala.

-- 1:1
CREATE TABLE message (
  message_id bigint, message_from bigint, message_to bigint, content text, created_at timestamp,
  PRIMARY KEY (message_id)
);
-- Grupo (e na prática também 1:1, usando um channel_id por conversa)
CREATE TABLE group_message (
  channel_id bigint, message_id bigint, user_id bigint, content text, created_at timestamp,
  PRIMARY KEY ((channel_id), message_id)        -- partição por canal, ordenado por message_id
);

Partições que crescem para sempre

Com PRIMARY KEY ((channel_id), message_id), todas as mensagens de um canal ficam numa única partição. Um canal muito ativo, com anos de histórico, vira uma partição de muitos GB, que é lenta de ler, de compactar e de reparar no Cassandra. A solução usada pelo Discord é acrescentar um balde de tempo à chave de partição:

PRIMARY KEY ((channel_id, bucket), message_id)
-- bucket = janela fixa de tempo derivada do message_id (por exemplo, 10 dias)

Ler as últimas 50 mensagens consulta o balde atual (e, se ele tiver poucas mensagens, o anterior). Cada partição fica limitada a uma janela de tempo, então nenhuma cresce sem limite.

message_id precisa ser único e ordenável (timestamps colidem). Opções: auto_increment (não existe em NoSQL), Snowflake global, ou uma sequência local por canal, mais simples, porque a ordem só importa dentro de uma conversa.

Fluxo 1:1

Como o CS1 sabe onde B está? Um registro user_id → chat server (no Redis, atualizado na conexão) ou um message bus pub/sub em que cada chat server assina os canais dos seus usuários conectados.

Os três "checks": enviado, entregue, lido

  1. O cliente de A gera um client_message_id (UUID), mostra a mensagem com um relógio e envia pelo WebSocket.
  2. O servidor persiste e responde com um ack contendo o message_id oficial. A mensagem ganha ✓ (enviada). Se o ack não chegar em alguns segundos, o cliente reenvia com o mesmo client_message_id; o servidor vê que já o processou e devolve o mesmo ack, sem duplicar.
  3. Quando o aparelho de B recebe a mensagem, envia um evento "entregue" com o message_id. O servidor o encaminha a A: ✓✓.
  4. Quando B abre a conversa, o cliente envia "lido até o message_id X" (um único evento cobre todas as anteriores). A vê os ✓✓ azuis.

Repare que "lido até X" é um cursor, não um evento por mensagem: guardar (channel_id, user_id) → last_read_message_id é suficiente para calcular quantas mensagens não lidas existem e onde mostrar a linha "mensagens novas".

O registro de conexões

Para entregar a B, é preciso saber em que servidor ele está. Duas abordagens:

  • Registro explícito: ao conectar, o chat server grava conn:{user_id} → {server_id, device_id} no Redis com TTL, renovado pelo heartbeat. Para entregar, consulta o registro e envia ao servidor certo (por RPC ou por uma fila exclusiva daquele servidor). Um usuário com 3 aparelhos tem 3 entradas.
  • Pub/sub: cada chat server assina, num message bus (Redis pub/sub, NATS, Kafka), os tópicos dos usuários conectados a ele. Quem envia publica no tópico do destinatário sem saber onde ele está.

Quando um chat server cai

Um servidor com 200 mil conexões cai, e 200 mil clientes tentam reconectar no mesmo segundo, provavelmente derrubando o próximo servidor. Os clientes devem reconectar com backoff e jitter (espera aleatória de alguns segundos), e o service discovery deve espalhar as reconexões por vários servidores. Ao reconectar, cada cliente sincroniza pelo seu cursor, então nenhuma mensagem se perde: o que estava em trânsito já foi persistido antes da entrega.

Sincronização entre dispositivos

Cada dispositivo guarda cur_max_message_id, o último ID que viu. Ao reconectar, pede ao KV store todas as mensagens com message_id > cur_max_message_id (cujo destinatário é o usuário logado). Como cada dispositivo tem seu próprio cursor, todos convergem.

go/chat/presence.go: sequência por canal + presença com heartbeat
// Package chat contém duas peças de um sistema de chat:
//
//   - Presence: status online/offline via heartbeat. Em vez de marcar offline
//     a cada desconexão do WebSocket (redes móveis oscilam!), o cliente manda
//     um heartbeat a cada X s; se nada chegar em `timeout`, fica offline.
//   - Inbox com sequência por canal: cada mensagem de um canal 1:1 ou grupo
//     recebe um message_id crescente *local ao canal*, e o cliente sincroniza
//     pedindo "tudo depois do meu cur_max_message_id".
package chat

import (
	"sync"
	"time"
)

type Presence struct {
	mu       sync.Mutex
	timeout  time.Duration
	now      func() time.Time
	lastBeat map[string]time.Time
}

func NewPresence(timeout time.Duration, now func() time.Time) *Presence {
	if now == nil {
		now = time.Now
	}
	return &Presence{timeout: timeout, now: now, lastBeat: map[string]time.Time{}}
}

func (p *Presence) Heartbeat(user string) {
	p.mu.Lock()
	defer p.mu.Unlock()
	p.lastBeat[user] = p.now()
}

func (p *Presence) Online(user string) bool {
	p.mu.Lock()
	defer p.mu.Unlock()
	t, ok := p.lastBeat[user]
	return ok && p.now().Sub(t) <= p.timeout
}

// ---------------------------------------------------------------------------

type Message struct {
	ChannelID string
	Seq       int64 // crescente dentro do canal
	From      string
	Text      string
}

type Store struct {
	mu       sync.Mutex
	seq      map[string]int64 // em produção: INCR no Redis por canal, ou ID Snowflake
	messages map[string][]Message
}

func NewStore() *Store { return &Store{seq: map[string]int64{}, messages: map[string][]Message{}} }

func (s *Store) Append(channel, from, text string) Message {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.seq[channel]++
	m := Message{ChannelID: channel, Seq: s.seq[channel], From: from, Text: text}
	s.messages[channel] = append(s.messages[channel], m)
	return m
}

// Since devolve as mensagens com Seq > after — é o que um dispositivo pede ao reconectar.
func (s *Store) Since(channel string, after int64) []Message {
	s.mu.Lock()
	defer s.mu.Unlock()
	msgs := s.messages[channel]
	// Seq começa em 1 e é contíguo, então o índice é direto.
	if after >= int64(len(msgs)) {
		return nil
	}
	return append([]Message(nil), msgs[after:]...)
}

Chat em grupo

Grupos pequenos (≤ 100): a mensagem é copiada para a fila de sincronização (inbox) de cada membro. É simples, porque cada cliente só checa a própria inbox, e funciona bem para grupos pequenos; o WeChat usa essa abordagem com grupos de até 500. Para grupos enormes (canais do Discord/Slack com milhares de membros), copiar por membro é caro: guarda-se uma vez por canal, e cada cliente busca o canal (modelo pull, como o fanout on read).

E grupos grandes (Slack, Discord)?

Copiar cada mensagem para a inbox de cada membro funciona com 100 membros, mas um canal com 100 mil membros transformaria cada mensagem em 100 mil escritas. Nesse caso, inverte-se o modelo (como no fanout on read do news feed):

  • A mensagem é gravada uma vez, na partição do canal.
  • Em tempo real, ela é enviada só para os membros online com o canal aberto (os chat servers sabem quem são), normalmente poucos.
  • Os demais leem o canal quando o abrirem, a partir do seu cursor de leitura.
  • Contagem de não lidas vira "último número de sequência do canal − meu cursor", calculada sob demanda (por isso uma sequência por canal, sem buracos, é útil aqui; com Snowflake seria preciso contar).

Presença (online/offline)

  • Login: com o WebSocket aberto, o status vira online e last_active_at é gravado no KV.
  • Logout: status offline.
  • Desconexão: redes móveis oscilam o tempo todo (passar num túnel). Mudar o status a cada queda geraria uma tempestade de eventos. Solução: heartbeat. O cliente envia um a cada ~5 s, e só depois de ~30 s sem heartbeat o status vira offline.
  • Fanout de presença: publica a mudança num canal por par de amigos ou por usuário, que os amigos online assinam. Para grupos grandes, é caro: busque o status sob demanda (ao abrir o grupo ou o perfil).

Falhas e extras

  • Chat server cai: o service discovery fornece um novo servidor e os clientes reconectam e sincronizam pelo cursor.
  • Reenvio: o cliente reenvia mensagens não confirmadas, com um client_message_id para dedup no servidor.
  • Ordem: garantida por canal via message_id; Kafka particionado por channel_id preserva a ordem.
  • Mídia: upload para S3 via presigned URL; a mensagem leva só a referência; miniaturas e CDN.
  • E2E encryption: protocolo Signal; o servidor só retransmite bytes cifrados.
  • Cache no cliente: o histórico local reduz a carga.
  • Status de leitura (✓✓): eventos de "entregue" e "lido" no mesmo canal.

Simulação de entrevista

A está no servidor 7 e B no servidor 42. A envia uma mensagem. Mostre o caminho.

A envia pelo WebSocket ao servidor 7. O servidor 7 gera o message_id (sequência do canal A-B ou Snowflake), persiste no Cassandra (partição = channel_id), confirma para A com um ✓, e publica no message bus. Para saber onde B está, consulta o registro de sessões no Redis: B → [servidor 42 (celular), servidor 13 (laptop)]. Publica para os dois; cada servidor entrega pelo WebSocket correspondente. Se B não tiver nenhuma sessão, o evento vai ao serviço de push.

Por que persistir antes de entregar?

Para garantir durabilidade: se o servidor 42 cair no meio do caminho, a mensagem não se perde, porque quando B reconectar, o cliente pede tudo depois do seu cur_max_message_id. A entrega em tempo real é uma otimização sobre o histórico durável.

E se A enviar duas mensagens rapidamente e elas chegarem fora de ordem?

A ordem é definida pelo message_id no servidor, não pela chegada no cliente. O cliente ordena pelo id. Para que o servidor não inverta, as mensagens de um canal são processadas na mesma partição (por exemplo, Kafka com chave = channel_id), que é serial.

Como escalar para 500 milhões de conexões?

Um servidor bem ajustado segura centenas de milhares de WebSockets, então são alguns milhares de servidores. O LB precisa ser L4 ou suportar upgrade de WebSocket, e o balanceamento de conexões longas usa least-connections. Em deploys, drenamos conexões aos poucos para não causar uma tempestade de reconexões, e o cliente reconecta com backoff com jitter.

Quiz

Por que heartbeat para presença em vez de marcar offline ao fechar a conexão?
Só marca offline após X segundos sem heartbeat.
Como um novo dispositivo sabe quais mensagens buscar?
Cada dispositivo tem seu cursor e pede as mensagens com id maior que ele.
Melhor banco para bilhões de mensagens por dia, acessadas por conversa e em ordem?
Escrita horizontal e leitura ordenada dentro da partição.
