Capítulo 06 · Estudo de caso

Projete um key-value store distribuído

O estudo de caso mais "teórico" do livro: junta CAP, particionamento, replicação, quórum, vector clocks, detecção de falhas e o caminho de leitura e escrita de um storage engine. É basicamente o design do Amazon Dynamo e do Cassandra.

Ao final você saberá:

  • Escolher entre CP e AP para um KV store e justificar.
  • Explicar quórum (N, W, R), vector clocks, gossip, hinted handoff e Merkle trees.
  • Descrever os caminhos de escrita (commit log → memtable → SSTable) e de leitura (Bloom filter).
  • Rodar uma simulação de quórum e de conflitos em Go.

Requisitos

  • Operações put(key, value) e get(key); pares pequenos (menos de 10 KB).
  • Capacidade de armazenar muitos dados (big data).
  • Alta disponibilidade, resposta rápida mesmo com falhas.
  • Escalabilidade horizontal automática (adicionar e remover nós).
  • Consistência ajustável.
  • Baixa latência.

Versão de um nó só: uma hash table em memória. Para caber mais, compressão e dados frios em disco. Mas um nó não basta, então precisamos de um KV distribuído, e daí vem o CAP.

Escolhendo no CAP

Com 3 réplicas n1, n2, n3, se n3 fica isolado por uma partição de rede:

  • CP: bloqueia as escritas em n1 e n2 (não dá para garantir que n3 as receba), e o sistema fica indisponível para escrita. Bancos e saldos querem isso.
  • AP: continua aceitando leituras e escritas (n3 pode servir dado velho) e sincroniza quando a partição terminar. O Dynamo (carrinho de compras) escolheu AP: "adicionar ao carrinho" nunca pode falhar.

Para o nosso design: AP com consistência eventual e ajustável via quórum.

Componentes centrais

1. Particionamento de dados

Consistent hashing com vnodes: escala automática (adicionar/remover nós move pouco) e heterogeneidade (mais vnodes para máquinas maiores).

2. Replicação

Cada chave é replicada nos N primeiros servidores físicos distintos no sentido horário do anel, de preferência em DCs/racks diferentes.

3. Consistência: quórum

  • N=3, W=2, R=2 (W+R > N): leitura vê a última escrita; tolera 1 nó fora.
  • R=1, W=N: otimizado para leitura. W=1, R=N: otimizado para escrita.
  • W+R ≤ N: consistência eventual com latência mínima.

4. Resolução de conflitos: vector clocks

Em AP, dois clientes podem escrever na mesma chave em réplicas diferentes ao mesmo tempo. Como saber qual versão é a "correta"? Last-write-wins por timestamp é simples, mas perde escritas (os relógios entre máquinas não são confiáveis).

Um vector clock é uma lista [servidor: contador] por versão:

  1. Cliente escreve D1 via Sx: [Sx:1]
  2. Outro cliente lê D1, atualiza para D2 via Sx: [Sx:2]
  3. Um cliente lê D2 e escreve D3 via Sy: [Sx:2, Sy:1]
  4. Ao mesmo tempo, outro lê D2 e escreve D4 via Sz: [Sx:2, Sz:1]
  5. D3 e D4 são concorrentes (nenhuma é ancestral da outra): conflito. O próximo cliente que ler recebe as duas versões, reconcilia (no carrinho, a união dos itens) e grava D5 = [Sx:3, Sy:1, Sz:1].

Regra: X é ancestral de Y se todo contador de X ≤ o contador correspondente de Y. Se em alguns é menor e em outros maior, são concorrentes.

Desvantagens: complexidade empurrada para o cliente, que precisa reconciliar, e o vetor pode crescer (limite o tamanho e remova os pares mais antigos, o que o Dynamo considera aceitável na prática).

go/kvstore/vectorclock.go
// Package kvstore ilustra os blocos de um key-value store distribuído no
// estilo Dynamo: vector clocks para detectar conflitos e quórum (N, W, R)
// para equilibrar consistência e disponibilidade.
package kvstore

// VectorClock mapeia servidor -> contador. Uma versão D1 é ancestral de D2 se
// todos os contadores de D1 são <= aos de D2. Se nenhuma é ancestral da outra,
// as escritas foram concorrentes = conflito que o cliente precisa resolver.
type VectorClock map[string]uint64

type Order int

const (
	Before     Order = iota // a aconteceu antes de b
	After                   // a aconteceu depois de b
	Equal                   // mesma versão
	Concurrent              // conflito
)

// Increment registra uma escrita feita pelo servidor `node`.
func (vc VectorClock) Increment(node string) VectorClock {
	out := vc.Copy()
	out[node]++
	return out
}

func (vc VectorClock) Copy() VectorClock {
	out := make(VectorClock, len(vc))
	for k, v := range vc {
		out[k] = v
	}
	return out
}

// Compare determina a relação causal entre duas versões.
func Compare(a, b VectorClock) Order {
	aLess, bLess := false, false
	for k := range union(a, b) {
		switch {
		case a[k] < b[k]:
			aLess = true
		case a[k] > b[k]:
			bLess = true
		}
	}
	switch {
	case aLess && bLess:
		return Concurrent
	case aLess:
		return Before
	case bLess:
		return After
	default:
		return Equal
	}
}

// Merge produz o relógio de uma versão que "resolve" o conflito:
// máximo componente a componente.
func Merge(a, b VectorClock) VectorClock {
	out := VectorClock{}
	for k := range union(a, b) {
		out[k] = max(a[k], b[k])
	}
	return out
}

func union(a, b VectorClock) map[string]struct{} {
	keys := map[string]struct{}{}
	for k := range a {
		keys[k] = struct{}{}
	}
	for k := range b {
		keys[k] = struct{}{}
	}
	return keys
}
go/kvstore/quorum.go: coordenador com N, W, R e versões irmãs (siblings)
package kvstore

import (
	"errors"
	"sync"
)

// Versioned é um valor com seu vector clock.
type Versioned struct {
	Value string
	Clock VectorClock
}

// Replica simula um nó de armazenamento que pode estar fora do ar.
type Replica struct {
	Name string
	mu   sync.Mutex
	data map[string][]Versioned // pode guardar várias versões concorrentes (siblings)
	Down bool
}

func NewReplica(name string) *Replica { return &Replica{Name: name, data: map[string][]Versioned{}} }

func (r *Replica) put(key string, v Versioned) bool {
	r.mu.Lock()
	defer r.mu.Unlock()
	if r.Down {
		return false
	}
	// Descarta versões que a nova supera; mantém as concorrentes.
	var kept []Versioned
	for _, old := range r.data[key] {
		if Compare(old.Clock, v.Clock) == Concurrent {
			kept = append(kept, old)
		}
	}
	r.data[key] = append(kept, v)
	return true
}

func (r *Replica) get(key string) ([]Versioned, bool) {
	r.mu.Lock()
	defer r.mu.Unlock()
	if r.Down {
		return nil, false
	}
	return append([]Versioned(nil), r.data[key]...), true
}

// Cluster coordena leituras e escritas com quórum.
//
//	N = nº de réplicas da chave, W = acks para escrita, R = respostas para leitura.
//	W + R > N  → toda leitura enxerga pelo menos uma réplica com a última escrita.
//	R=1, W=N   → leitura rápida.   W=1, R=N → escrita rápida.
type Cluster struct {
	Replicas []*Replica
	N, W, R  int
}

var ErrQuorum = errors.New("kvstore: quórum não atingido")

// Put grava em todas as N réplicas e só confirma se W responderem.
// `ctx` é o clock lido antes (read-modify-write); `coordinator` é quem grava.
func (c *Cluster) Put(key, value string, ctx VectorClock, coordinator string) error {
	v := Versioned{Value: value, Clock: ctx.Increment(coordinator)}
	acks := 0
	for _, r := range c.Replicas[:c.N] {
		if r.put(key, v) {
			acks++
		}
	}
	if acks < c.W {
		return ErrQuorum
	}
	return nil
}

// Get consulta as réplicas até obter R respostas e devolve as versões mais
// recentes (mais de uma = conflito para o cliente reconciliar).
func (c *Cluster) Get(key string) ([]Versioned, error) {
	var all []Versioned
	answers := 0
	for _, r := range c.Replicas[:c.N] {
		vs, ok := r.get(key)
		if !ok {
			continue
		}
		answers++
		all = append(all, vs...)
		if answers == c.R {
			break
		}
	}
	if answers < c.R {
		return nil, ErrQuorum
	}
	return latest(all), nil
}

// latest remove versões dominadas por outras e duplicadas.
func latest(vs []Versioned) []Versioned {
	var out []Versioned
	for i, a := range vs {
		dominated := false
		for j, b := range vs {
			if i == j {
				continue
			}
			o := Compare(a.Clock, b.Clock)
			if o == Before || (o == Equal && j < i) {
				dominated = true
				break
			}
		}
		if !dominated {
			out = append(out, a)
		}
	}
	return out
}
go/kvstore/kvstore_test.go (trecho): o carrinho com conflito
func TestConcurrentWritesProduceSiblings(t *testing.T) {
	c := newCluster(3, 1, 3)
	_ = c.Put("cart", "[livro]", nil, "A")
	base, _ := c.Get("cart")
	// Dois clientes leem a mesma versão e escrevem via coordenadores diferentes.
	_ = c.Put("cart", "[livro, caneta]", base[0].Clock, "A")
	_ = c.Put("cart", "[livro, café]", base[0].Clock, "B")
	vs, _ := c.Get("cart")
	if len(vs) != 2 {
		t.Fatalf("esperava 2 versões em conflito, got %v", vs)
	}
	// Cliente reconcilia (ex.: união do carrinho) e grava com o clock mesclado.
	merged := Merge(vs[0].Clock, vs[1].Clock)
	_ = c.Put("cart", "[livro, caneta, café]", merged, "A")
	vs, _ = c.Get("cart")
	if len(vs) != 1 || vs[0].Value != "[livro, caneta, café]" {
		t.Fatalf("conflito não resolvido: %v", vs)
	}
}

5. Tratamento de falhas

Detecção (gossip): com muitos nós, multicast para todos (O(N²)) não escala. No protocolo de gossip:

  • Cada nó mantém uma lista de membros com IDs e contadores de heartbeat.
  • Periodicamente incrementa o próprio contador e envia a lista a alguns nós aleatórios, que a repassam.
  • Se o contador de um nó não aumenta por um tempo, ele é considerado offline. Exigir que mais de uma fonte confirme a queda evita falsos positivos.

Falhas temporárias: sloppy quorum + hinted handoff. Em vez de exigir as N réplicas "oficiais", o coordenador usa os primeiros W/R nós saudáveis do anel. Se s2 está fora, s3 recebe a escrita com uma "dica" (hint) e a entrega a s2 quando ele voltar.

Falhas permanentes: anti-entropy com Merkle trees. Para sincronizar réplicas sem comparar todas as chaves, cada réplica divide o espaço de chaves em buckets, calcula o hash de cada bucket e monta uma árvore de hashes. Comparando as raízes: se iguais, as réplicas estão sincronizadas; se diferentes, desce pelos filhos diferentes até achar os buckets divergentes. A quantidade de dados transferidos é proporcional às diferenças, não ao tamanho total.

Falha de datacenter: réplicas em vários DCs.

Arquitetura do sistema

Cada nó cuida de: API de cliente, detecção de falhas, resolução de conflitos, reparo de falhas, replicação e storage engine. Não há ponto único de falha.

Caminho de escrita (LSM tree, como no Cassandra)

  1. A escrita é gravada no commit log (append em disco: durabilidade e recuperação de crash).
  2. É gravada na memtable (estrutura ordenada em memória).
  3. Quando a memtable enche, é descarregada (flush) para disco como uma SSTable (Sorted String Table, imutável).
  4. Compaction em background funde SSTables, remove versões antigas e tombstones.

Tudo é escrita sequencial, por isso as LSM trees são tão rápidas para escrever (lembre: seek em disco é caro).

Caminho de leitura

  1. Procura na memtable; se achar, retorna.
  2. Senão, consulta o Bloom filter de cada SSTable para saber quais podem conter a chave, e evita ler as que certamente não têm.
  3. Lê as SSTables candidatas (da mais nova para a mais antiga) e retorna o valor.
go/bloom/bloom.go
// Package bloom implementa um Bloom filter: estrutura probabilística que
// responde "com certeza NÃO está" ou "provavelmente está" usando poucos bits.
//
// Onde aparece em system design:
//   - Web crawler: "já visitei esta URL?" sem guardar bilhões de strings.
//   - LSM trees (Cassandra, RocksDB, Bigtable): evita ler SSTables que não têm a chave.
//   - Encurtador com hash: checar colisão antes de ir ao banco.
package bloom

import (
	"hash/fnv"
	"math"
)

type Filter struct {
	bits []uint64
	m    uint64 // nº de bits
	k    uint64 // nº de funções de hash
}

// New dimensiona o filtro para n itens com taxa de falso positivo p:
//
//	m = -n·ln(p) / (ln 2)²     k = (m/n)·ln 2
//
// Ex.: 1 bilhão de URLs com p=1% ≈ 9,6 bits/item ≈ 1,2 GB — cabe em memória.
func New(n int, p float64) *Filter {
	m := uint64(math.Ceil(-float64(n) * math.Log(p) / (math.Ln2 * math.Ln2)))
	k := uint64(math.Round(float64(m) / float64(n) * math.Ln2))
	return &Filter{bits: make([]uint64, (m+63)/64), m: m, k: max(k, 1)}
}

// Double hashing (Kirsch–Mitzenmacher): gi(x) = h1 + i·h2 simula k hashes.
func (f *Filter) hashes(s string) (uint64, uint64) {
	h := fnv.New64a()
	h.Write([]byte(s))
	a := h.Sum64()
	return a, (a >> 33) | 1
}

func (f *Filter) Add(s string) {
	h1, h2 := f.hashes(s)
	for i := uint64(0); i < f.k; i++ {
		pos := (h1 + i*h2) % f.m
		f.bits[pos/64] |= 1 << (pos % 64)
	}
}

func (f *Filter) MightContain(s string) bool {
	h1, h2 := f.hashes(s)
	for i := uint64(0); i < f.k; i++ {
		pos := (h1 + i*h2) % f.m
		if f.bits[pos/64]&(1<<(pos%64)) == 0 {
			return false
		}
	}
	return true
}

Simulação de entrevista

Projete um KV store distribuído para guardar carrinhos de compra de um e-commerce global.

Para carrinho, a prioridade é que "adicionar item" nunca falhe; perder uma venda é pior que mostrar um carrinho levemente desatualizado. Então vou para AP com consistência eventual. Os valores são pequenos, alguns KB, e o acesso é sempre por cart_id. Confirma que não há consultas por outros campos?

Confirmo. Só get e put por id.

Particionamento por consistent hashing com vnodes; cada chave replicada em N=3 nós em zonas diferentes. Uso quórum W=2, R=2 por padrão, configurável por chamada. Qualquer nó pode ser coordenador, então não há mestre para cair.

Dois dispositivos do mesmo usuário adicionam itens diferentes durante uma partição. O que acontece?

Cada escrita recebe um vector clock. Quando a partição termina, a leitura encontra duas versões concorrentes e devolve as duas. Para carrinho, a reconciliação é a união dos itens, feita pelo serviço de carrinho, que grava a versão mesclada. O efeito colateral conhecido é que um item removido pode "ressuscitar"; para evitar, guardo remoções como marcadores (estilo CRDT OR-Set).

E se um nó morre de vez?

Gossip detecta. Enquanto isso, sloppy quorum e hinted handoff mantêm as escritas aceitas. Se não voltar, o anel é reconfigurado, os vizinhos assumem os trechos e a anti-entropy com Merkle trees copia só os dados que faltam para as novas réplicas.

Como o storage em cada nó é organizado?

LSM tree: commit log + memtable, flush para SSTables imutáveis e compaction em background. Leituras usam Bloom filter por SSTable para evitar I/O desnecessário. É ótimo para o perfil de muitas escritas de um carrinho.

Follow-ups

Por que não last-write-wins (LWW)?

É mais simples (Cassandra usa por padrão), mas descarta silenciosamente uma das escritas concorrentes e depende de relógios sincronizados. Aceitável quando sobrescrever é a semântica desejada (último status, perfil); inaceitável quando as escritas devem ser combinadas (carrinho, contadores).

O que é read repair?

Na leitura com R > 1, se o coordenador vê réplicas com versões antigas, ele envia a versão nova para elas. Corrige divergências "de graça" nas chaves que são lidas; a anti-entropy cuida do resto.

B-tree × LSM tree?

B-tree (Postgres, MySQL): atualiza no lugar; leitura rápida e previsível; escrita com I/O aleatório. LSM (Cassandra, RocksDB): escrita sequencial muito rápida; leitura pode consultar vários arquivos (mitigado por Bloom filters e compaction); amplificação de escrita na compaction.

CRDTs?

Tipos de dados que convergem automaticamente sem coordenação (contadores G-Counter/PN-Counter, conjuntos OR-Set). Úteis em multi-líder e edição colaborativa; eliminam a reconciliação manual para certos tipos.

Quiz

Vector clocks [A:2, B:1] e [A:1, B:2]. Relação?
A é maior no primeiro e B é maior no segundo; nenhum domina o outro.
Uma réplica fica fora por 5 minutos. Qual mecanismo mantém as escritas aceitas e depois a atualiza?
Outro nó guarda a escrita com uma dica e a entrega quando a réplica voltar. Merkle trees são para divergências maiores ou permanentes.
Para que serve o Bloom filter no caminho de leitura?
"Não está" é garantido, o que evita I/O desnecessário.
Por que Merkle trees na anti-entropy?
Comparar raízes e descer pelos ramos diferentes localiza os buckets divergentes rapidamente.
