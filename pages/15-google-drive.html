Projete o Google Drive

Armazenamento e sincronização de arquivos (Drive, Dropbox, OneDrive). Desafios: não perder dados nunca, sincronizar vários dispositivos, economizar banda e lidar com edições conflitantes.

Ao final você saberá:

  • Evoluir de um servidor único para uma arquitetura com S3, block servers e metadados.
  • Dividir arquivos em blocos, fazer delta sync e deduplicar.
  • Escolher long polling para notificar mudanças.
  • Tratar conflitos de sincronização e garantir consistência dos metadados.

  • 2 uploads/dia de 500 KB em média; leitura:escrita de 1:1.
  • QPS de upload: 10 M × 2 / 105 ≈ 240; pico ~480.

Evolução do design

Servidor único: Apache + MySQL + diretório drive/namespace/arquivo. Logo o disco enche.

Evolução:

  1. Arquivos no S3, com replicação entre regiões (durabilidade).
  2. Load balancer e web servers stateless.
  3. Metadados (usuários, arquivos, blocos, versões) num banco separado, replicado e sharded.

Deep dive: blocos, delta sync e deduplicação

  • Delta sync: ao modificar um arquivo, só os blocos alterados são enviados (o rsync faz algo semelhante).
  • Compressão por tipo: gzip/bzip2 para texto; codecs específicos para mídia.
  • Deduplicação: blocos com o mesmo hash são armazenados uma única vez, mesmo entre arquivos e usuários diferentes.
  • Retomada: uploads grandes continuam de onde pararam (bloco a bloco; S3 multipart).
go/filesync/blocks.go
// Package filesync mostra a técnica central de um Google Drive / Dropbox:
// dividir arquivos em blocos, identificar cada bloco pelo hash do conteúdo e,
// numa atualização, enviar só os blocos que mudaram (delta sync).
//
// Benefícios: menos banda, retomada de upload, deduplicação entre arquivos e
// usuários (mesmo hash = mesmo bloco guardado uma vez no object storage).
package filesync

import (
	"crypto/sha256"
	"encoding/hex"
)

// Block é a unidade de upload/armazenamento (Dropbox usa até 4 MB).
type Block struct {
	Index int
	Hash  string
	Data  []byte
}

// Split divide os dados em blocos de tamanho fixo.
func Split(data []byte, size int) []Block {
	var out []Block
	for i := 0; i*size < len(data); i++ {
		end := min((i+1)*size, len(data))
		chunk := data[i*size : end]
		sum := sha256.Sum256(chunk)
		out = append(out, Block{Index: i, Hash: hex.EncodeToString(sum[:]), Data: chunk})
	}
	return out
}

// Manifest é o que o serviço de metadados guarda por versão de arquivo:
// a lista ordenada de hashes. O conteúdo vive no object storage (S3).
func Manifest(blocks []Block) []string {
	m := make([]string, len(blocks))
	for i, b := range blocks {
		m[i] = b.Hash
	}
	return m
}

// Changed devolve os blocos da nova versão que o servidor ainda não tem.
// `known` = conjunto de hashes já armazenados (de qualquer arquivo → dedup).
func Changed(newBlocks []Block, known map[string]bool) []Block {
	var out []Block
	for _, b := range newBlocks {
		if !known[b.Hash] {
			out = append(out, b)
		}
	}
	return out
}

Bônus: chunking por conteúdo (CDC) Com blocos de tamanho fixo, inserir um byte no início desloca todos os blocos seguintes e todos os hashes mudam. Content-defined chunking (rolling hash, como Rabin fingerprint) define as fronteiras pelo conteúdo, então uma inserção afeta só os blocos vizinhos. Muito usado em backup (restic, borg).

Deep dive: alta consistência

Usuários diferentes não podem ver versões diferentes do mesmo arquivo ao mesmo tempo. Os metadados exigem consistência forte: um relacional com ACID (a escolha natural) ou um NoSQL com transações. O cache de metadados precisa ser invalidado na escrita, e réplicas de cache e banco devem estar consistentes.

Fluxo de upload

Download: o cliente é notificado (ou consulta ao reconectar), pede os metadados atualizados, descobre quais blocos faltam e baixa só esses dos block servers, montando o arquivo localmente.

Serviço de notificação: long polling × WebSocket

O Dropbox usa long polling, e faz sentido: a comunicação é unidirecional (servidor avisa "há mudanças"), as notificações são pouco frequentes e não há rajadas de dados. WebSocket seria mais adequado para comunicação bidirecional e em tempo real, como chat. Ao receber a resposta (ou timeout), o cliente busca as mudanças nos metadados e abre um novo long poll.

Conflitos de sincronização

Dois usuários (ou dispositivos) editam o mesmo arquivo ao mesmo tempo. Estratégia: a primeira versão processada vence; a outra recebe um conflito. O cliente fica com as duas cópias (arquivo.txt e arquivo (cópia em conflito de Ana).txt) e o usuário escolhe como mesclar.

A detecção usa a versão base: o cliente envia "minha edição parte da versão 7"; se o servidor já está na versão 8, há conflito. É lock otimista com UPDATE file SET latest_version = 8 WHERE id = ? AND latest_version = 7.

Economizando espaço

  • Deduplicação de blocos por hash na conta (ou globalmente).
  • Política de backup inteligente: limitar o número de versões guardadas; manter só versões importantes (as edições frequentes de um documento grande criam muitas versões).
  • Dados frios para cold storage (meses sem acesso).

Falhas

  • LB: par ativo/passivo com heartbeat.
  • Block server: outros assumem os jobs pendentes.
  • Cloud storage: buckets replicados em várias regiões.
  • API server: stateless.
  • Metadata cache/DB: réplicas; promover uma nova primária.
  • Notification service: cada servidor segura muitas conexões long poll; se cair, os clientes reconectam a outro (reconexão em massa é lenta: limite e espalhe).
  • Offline backup queue: filas replicadas.

Simulação de entrevista

Uma usuária edita uma linha num arquivo de 2 GB. Quanto ela envia?

Com blocos de 4 MB, o cliente recalcula os hashes, compara com o manifest da versão anterior e envia só o bloco alterado: ~4 MB em vez de 2 GB, e menos ainda comprimido. Se a edição inseriu bytes (em vez de sobrescrever), blocos de tamanho fixo deslocariam tudo depois do ponto de inserção; com content-defined chunking, só um ou dois blocos mudam.

Por que separar os block servers dos API servers?

São cargas muito diferentes. Block servers lidam com bytes: CPU para hash, compressão e criptografia, e muita banda. API servers lidam com metadados: muitas requisições pequenas e transacionais. Separados, cada um escala no seu eixo. Uma alternativa é o cliente fazer o chunking e mandar direto para o S3 com presigned URLs, tirando os bytes dos nossos servidores, mas aí a criptografia e a deduplicação ficam no cliente.

Dois laptops da mesma pessoa editaram o arquivo offline. Ela conecta os dois. E agora?

O primeiro a sincronizar envia "edição sobre a versão 7"; o servidor aceita e vira a versão 8. O segundo também diz "sobre a versão 7", mas o servidor está na 8: conflito. Esse cliente baixa a versão 8, renomeia a sua como cópia em conflito e envia as duas. Nada se perde e a decisão fica com a usuária.

Quiz

Por que long polling no serviço de notificação?
WebSocket compensa quando há tráfego bidirecional frequente.
O que permite deduplicar arquivos entre usuários?
Mesmo hash, mesmo conteúdo: guardado uma vez.
Qual parte do sistema exige consistência forte?
Os blocos são imutáveis; quem decide "qual é a versão atual" são os metadados.
