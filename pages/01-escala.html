Capítulo 01 · Fundamentos

De zero a milhões de usuários

A evolução de uma arquitetura, passo a passo. Cada passo resolve o gargalo do anterior, e entender qual gargalo cada peça resolve é o vocabulário básico de toda entrevista de system design.

Ao final você saberá:

  • Explicar o papel de DNS, load balancer, réplicas de banco, cache, CDN, filas e sharding.
  • Escolher entre SQL e NoSQL e entre escala vertical e horizontal, com justificativa.
  • Tornar a camada web stateless e entender por que isso habilita o autoscaling.
  • Descrever uma arquitetura multi-datacenter e seus desafios.

Passo 0: um único servidor

Tudo começa numa máquina: app web, banco de dados e cache juntos. O fluxo de uma requisição:

  1. O usuário digita api.meusite.com. O DNS (normalmente um serviço gerenciado como Route 53 ou Cloudflare) devolve o IP do servidor.
  2. O navegador ou app envia HTTP para esse IP.
  3. O servidor responde com HTML (site) ou JSON (API para apps móveis).

O que acontece numa requisição, por dentro

Vale saber o caminho completo, porque cada etapa é um lugar onde dá para ganhar ou perder latência:

  1. Resolução DNS. O sistema operacional pergunta a um resolver recursivo (do provedor, ou 8.8.8.8). Se ele não tem a resposta em cache, consulta em cadeia: servidores raiz → servidor do TLD (.com) → servidor autoritativo do domínio, que devolve o registro A (IPv4) ou AAAA (IPv6). A resposta vem com um TTL: por quanto tempo resolvers e navegadores podem guardá-la em cache.
  2. Conexão TCP. Handshake de 3 vias (SYN, SYN-ACK, ACK): custa 1 ida e volta (RTT) antes de enviar qualquer byte.
  3. TLS. Negociação de chaves para HTTPS: mais 1 RTT no TLS 1.3 (2 no 1.2).
  4. HTTP. A requisição em si, mais 1 RTT, somado ao tempo de processamento no servidor.

Com um RTT de 100 ms (usuário no Brasil, servidor nos EUA), uma primeira requisição custa ~300 ms só de rede, antes de o servidor fazer qualquer coisa. É por isso que CDN, edge e reaproveitamento de conexões (keep-alive, HTTP/2) importam tanto: eles atacam os RTTs, não o código.

Por que o TTL do DNS importa para system design O TTL decide a velocidade de um failover via DNS. Se o registro tem TTL de 1 hora e o servidor morre, parte dos clientes vai continuar tentando o IP antigo por até 1 hora. Serviços que dependem de failover por DNS usam TTL curto (30–60 s), ao custo de mais consultas. Outro ponto: muitos clientes ignoram o TTL e guardam o IP por mais tempo, então DNS sozinho nunca é um mecanismo de failover instantâneo.

Passo 1: separar o banco de dados

Com mais usuários, separamos a camada web (tráfego) da camada de dados. Agora cada uma pode escalar de forma independente.

Regra prática para a entrevista Comece com relacional: é o padrão seguro e resolve 90% dos casos. Mude para NoSQL quando houver um motivo concreto: (1) latência muito baixa; (2) dados não estruturados ou sem relações; (3) só precisa serializar/deserializar (JSON, YAML); (4) volume massivo de escrita ou dados (TB/PB), por exemplo eventos, mensagens de chat ou métricas.

Como pensar: em SQL você modela os dados (normaliza) e depois escreve qualquer query. Em NoSQL você modela as queries: primeiro lista os padrões de acesso ("buscar as últimas 50 mensagens de uma conversa") e desenha a chave para que cada padrão vire uma leitura numa única partição. Se os padrões de acesso ainda não são conhecidos, isso é um forte argumento a favor de SQL.

Exemplo: mensagens de chat Em Cassandra, uma tabela messages com partition key conversation_id e clustering key message_id DESC faz "últimas 50 mensagens da conversa X" ser uma leitura sequencial de uma única partição em um único nó. Em Postgres a mesma query funciona com um índice em (conversation_id, message_id); o problema só aparece quando o volume de escrita passa do que um primário aguenta (dezenas de milhares de mensagens por segundo).

Passo 2: escala vertical × horizontal

Vertical (scale up): máquina maior
  • Simples: zero mudança no código.
  • Ótima com pouco tráfego.
  • Mas tem limite físico, custo exponencial e nenhum failover: se cair, cai tudo.
Horizontal (scale out): mais máquinas
  • Escala quase ilimitada e redundância.
  • Exige load balancer, serviço stateless e dados particionados.
  • Mais complexidade operacional.

Não subestime a escala vertical. Uma única máquina de nuvem grande hoje tem centenas de núcleos e terabytes de RAM, e um Postgres bem indexado nela aguenta dezenas de milhares de transações simples por segundo. Muitos produtos bem-sucedidos rodam por anos com um banco primário vertical e uma camada web horizontal.

A regra que costuma valer na prática: a camada web escala horizontalmente desde cedo (é barato, porque ela é stateless), e a camada de dados escala verticalmente o máximo possível antes de partir para sharding (que é caro em complexidade). Na entrevista, diga isso explicitamente: mostra que você sabe onde está a dificuldade real.

O custo escondido do horizontal Com 1 máquina, uma operação é local e atômica. Com N máquinas, você ganha problemas que não existiam: a rede falha e atrasa, os relógios divergem, uma máquina pode estar lenta em vez de morta, e você precisa decidir o que acontece quando metade do sistema não enxerga a outra metade. Os conceitos para lidar com isso estão em Sistemas distribuídos.

Passo 3: load balancer

O LB recebe todo o tráfego num IP público e o distribui entre servidores web, que agora só têm IPs privados (mais seguro). Se o servidor 1 cai, o tráfego vai para o 2; se o tráfego cresce, adicionamos o servidor 3.

  • Algoritmos: round robin, least connections, IP hash, weighted.
  • L4 × L7: L4 (TCP/UDP) é rápido e não olha o conteúdo; L7 (HTTP) roteia por path/header, termina TLS e faz retries. Detalhes em Ferramentas.
  • Health checks tiram do pool os servidores doentes.
  • O próprio LB é redundante (par ativo-passivo ou serviço gerenciado como ALB/NLB).

Os algoritmos de balanceamento, explicados

AlgoritmoComo funcionaQuando usarArmadilha
Round robinManda para o servidor 1, 2, 3, 1, 2, 3…Servidores iguais, requisições de custo parecidoSe uma requisição demora 10 s e outra 10 ms, a carga real fica desigual
Weighted round robinServidor com peso 2 recebe o dobroMáquinas de tamanhos diferentes; canary (1% do tráfego para a versão nova)Pesos estáticos não reagem à carga real
Least connectionsManda para quem tem menos conexões abertasRequisições de duração variável, WebSockets, conexões longasUm servidor recém-adicionado (com zero conexões) recebe uma avalanche
Least response time / P2CSorteia 2 servidores e escolhe o menos carregado (power of two choices)Padrão moderno em proxies como Envoy; quase tão bom quanto olhar todos, muito mais baratoPrecisa de métricas de carga por servidor
IP hash / consistent hashMesmo cliente (ou mesma chave) cai sempre no mesmo servidorAfinidade: cache local por usuário, servidores com estadoDistribuição desigual se poucos clientes geram muito tráfego (um NAT corporativo)

Health checks e connection draining

  • Ativo: o LB chama GET /health a cada poucos segundos. Após N falhas seguidas, tira o servidor do pool; após M sucessos, devolve. O endpoint deve checar o que importa (o processo responde, consegue falar com o banco), mas sem derrubar o servidor se uma dependência opcional cair, ou um problema no banco tira todos os servidores do pool ao mesmo tempo.
  • Passivo: o LB observa respostas reais (5xx, timeouts) e ejeta servidores ruins (outlier detection).
  • Draining: num deploy ou scale-in, o servidor sai do pool para conexões novas, mas termina as que estão em andamento antes de desligar. Sem isso, cada deploy derruba requisições.
Como o próprio LB não vira ponto único de falha Três formas comuns: (1) par ativo-passivo com IP virtual: dois LBs, o passivo monitora o ativo e assume o IP se ele parar de responder (keepalived/VRRP); (2) vários LBs com DNS: o domínio resolve para vários IPs, cada um de um LB; (3) anycast: o mesmo IP é anunciado de vários lugares e a rede entrega ao mais próximo (é assim que Cloudflare e Google funcionam). Na nuvem, um ALB/NLB gerenciado já resolve isso por você.

Passo 4: replicação do banco

O modelo mais comum é primário–réplicas (master–slave): só o primário aceita escritas, e as réplicas recebem cópias e atendem leituras. A maioria das aplicações tem muito mais leitura que escrita, então isso multiplica a capacidade.

  • Desempenho: leituras em paralelo entre réplicas.
  • Confiabilidade: dados em várias máquinas, até em regiões diferentes.
  • Disponibilidade: se uma réplica cai, as leituras vão para outra. Se o primário cai, uma réplica é promovida (failover).
Cuidado com o atraso de replicação (replication lag) Replicação assíncrona significa que uma réplica pode estar alguns ms ou segundos atrasada. Exemplo clássico: o usuário edita o perfil, a página recarrega lendo de uma réplica e mostra o dado antigo. Soluções: read-your-writes (ler do primário por alguns segundos depois de uma escrita do próprio usuário), roteamento por sessão, ou replicação síncrona para dados críticos (mais lenta). No failover, a réplica promovida pode não ter as últimas escritas, e isso exige reconciliação.

Síncrona, assíncrona ou semi-síncrona

ModoO primário confirma a escrita quando…PrósContras
Assíncronagravou localmente; réplicas recebem depoisEscrita rápida; réplica lenta não atrapalhaSe o primário morre, as escritas ainda não replicadas se perdem; réplicas ficam atrasadas
Síncronatodas as réplicas confirmaramNenhuma perda; réplicas sempre atualizadasLatência da réplica mais lenta; se uma réplica cai, as escritas param
Semi-síncronapelo menos 1 réplica confirmouGarante que o dado existe em 2 máquinas sem depender de todasUm pouco mais lenta que assíncrona

A maioria dos bancos gerenciados usa assíncrona para réplicas de leitura e semi-síncrona ou síncrona para a réplica "de standby" que assume no failover (por exemplo, o Multi-AZ do RDS).

Como funciona um failover, passo a passo

  1. Detecção: um monitor (ou as próprias réplicas) percebe que o primário não responde há X segundos. Escolher X é um trade-off: curto demais gera failovers falsos numa simples pausa de rede; longo demais deixa o sistema sem escrita por mais tempo.
  2. Eleição: escolhe-se a réplica mais atualizada (a que recebeu mais do log de replicação).
  3. Reconfiguração: as outras réplicas passam a seguir o novo primário, e as aplicações passam a escrever nele (via DNS, proxy ou endpoint do serviço gerenciado).
  4. Cerca (fencing): o primário antigo, se voltar, precisa ser impedido de aceitar escritas.
Split brain Se o primário antigo só estava isolado da rede (não morto) e continua aceitando escritas enquanto um novo primário foi eleito, você tem dois primários divergindo: o split brain. Os dados escritos em cada lado entram em conflito. A defesa é exigir maioria (quórum) para eleger um líder e usar um fencing token (um número de época que aumenta a cada eleição; o armazenamento rejeita escritas com época antiga). Mais em Sistemas distribuídos.

Além do primário–réplicas

  • Multi-líder: cada região tem um primário que aceita escritas e replica para os outros. Ótimo para multi-região, mas escritas concorrentes no mesmo dado geram conflitos que precisam de regra de resolução (last-write-wins, merge).
  • Sem líder (leaderless): o cliente escreve em várias réplicas e lê de várias, com quórum (W + R > N). É o modelo do Dynamo e do Cassandra, detalhado no capítulo 06.

Passo 5: cache

Cache é armazenamento temporário em memória para dados lidos com frequência ou caros de calcular. Ler da RAM leva ~100 ns; ler do banco pela rede, alguns ms.

Padrão mais comum, cache-aside (read-through feito pela aplicação): procura no cache; num miss, lê do banco e grava no cache.

go/cache/lru.go (trecho): LRU com TTL e cache-aside
// GetOrLoad implementa cache-aside. `load` é a ida ao banco.
func (c *LRU[V]) GetOrLoad(key string, load func(string) (V, error)) (V, error) {
	if v, ok := c.Get(key); ok {
		return v, nil
	}
	v, err := load(key)
	if err != nil {
		return v, err
	}
	c.Set(key, v)
	return v, nil
}

Considerações ao usar cache

PontoO que dizer na entrevista
Quando usarDados lidos muito mais do que escritos. Cache é volátil: nunca é a fonte da verdade.
Expiração (TTL)Curta demais gera muitas idas ao banco; longa demais serve dado velho.
ConsistênciaBanco e cache não são atualizados atomicamente. Prefira invalidar (delete) a atualizar o cache na escrita.
FalhasUm único nó de cache é SPOF. Use vários nós (Redis Cluster) e superdimensione a memória.

Thundering herdChave popular expira e mil requisições vão ao banco juntas. Mitigue com lock/single-flight, TTL com jitter e refresh antecipado.

Por que o cache ajuda tanto: a conta

Suponha 10.000 leituras/s, banco com latência de 5 ms e cache com 0,5 ms.

Hit rateLeituras/s que chegam ao bancoLatência média
0% (sem cache)10.0005 ms
80%2.0000,8 × 0,5 + 0,2 × 5,5 = 1,5 ms
95%5000,95 × 0,5 + 0,05 × 5,5 = 0,75 ms
99%1000,55 ms

Note duas coisas. Primeiro, ir de 95% para 99% de hit rate corta a carga no banco em 5×: os últimos pontos percentuais valem muito. Segundo, a conta inversa também vale: se o cache cair, o banco recebe de repente 20× ou 100× mais carga do que está acostumado e provavelmente cai junto. Um cache que segura a maior parte do tráfego deixou de ser otimização e virou dependência crítica; trate-o com a mesma redundância do banco.

Onde dá para colocar cache

  1. Cliente (navegador, app): headers Cache-Control, ETag. A requisição mais rápida é a que não acontece.
  2. CDN: estáticos e respostas públicas.
  3. Memória local do servidor: zero rede, mas cada servidor tem sua cópia (inconsistência entre servidores, memória duplicada). Bom para dados pequenos e quase imutáveis, como configurações.
  4. Cache distribuído (Redis/Memcached): compartilhado por todos os servidores. O padrão quando se fala em "cache" na entrevista.
  5. Banco: buffer pool, views materializadas.

Estratégias de escrita

EstratégiaComo funcionaQuando usar
Cache-aside (lazy loading)A aplicação lê do cache; num miss, lê do banco e popula. Na escrita, grava no banco e apaga a chave no cache.Padrão geral. Só cacheia o que é lido de fato.
Read-throughIgual ao cache-aside, mas é a biblioteca/camada de cache que vai ao banco, não a aplicação.Quando você quer esconder o banco atrás do cache.

Por que apagar, e não atualizar, o cache na escrita

Imagine duas escritas concorrentes no mesmo usuário, A (nome = "Ana") e B (nome = "Bia"). Se cada uma faz "grava no banco, depois atualiza o cache", a ordem pode intercalar assim: A grava no banco, B grava no banco, B atualiza o cache, A atualiza o cache. Banco = "Bia", cache = "Ana", e fica errado até o TTL vencer. Se em vez de atualizar você apaga, a próxima leitura busca o valor correto no banco. Ainda existe uma janela rara de inconsistência (uma leitura lenta pode repopular com valor antigo), e é por isso que todo cache deve ter TTL, mesmo que longo: ele limita por quanto tempo um erro pode durar.

Políticas de evicção

  • LRU (least recently used): remove o que foi usado há mais tempo. Bom padrão: o que foi acessado recentemente tende a ser acessado de novo.
  • LFU (least frequently used): remove o menos acessado no total. Melhor quando há itens "sempre populares", mas demora a esquecer algo que foi popular e deixou de ser.
  • FIFO / aleatório: simples e baratos; o Redis usa LRU aproximado por amostragem justamente porque LRU exato custa memória.

Chaves quentes (hot keys)

Em um cache distribuído, cada chave mora em um nó. Se uma chave recebe 200 mil leituras/s (a página de um evento ao vivo), aquele nó satura enquanto os outros ficam ociosos. Soluções: cache local no servidor de aplicação por poucos segundos para as chaves mais quentes, ou replicar a chave com sufixos (evento:42#1 … evento:42#8) e ler de um sufixo aleatório.

Passo 6: CDN

Uma CDN é uma rede de servidores geograficamente distribuídos (edge/PoPs) que cacheia conteúdo estático (imagens, vídeos, CSS, JS) perto do usuário. Um usuário em Lisboa baixa a imagem de um PoP em Lisboa, não do servidor em São Paulo.

  1. O usuário pede cdn.site.com/logo.png.
  2. Se o PoP não tem o arquivo, busca na origem (servidor ou S3) e cacheia conforme o header Cache-Control/TTL.
  3. Os próximos usuários da região recebem direto do PoP.

Considerações: custo (você paga por transferência, então não cacheie o que é pouco acessado), TTL adequado, fallback para a origem se a CDN falhar, invalidação (API da CDN ou versionamento de URL: app.v42.js).

Pull × push

  • Pull CDN (o modelo acima): a CDN busca na origem no primeiro acesso. Zero trabalho para você; o primeiro usuário de cada região paga a latência do miss. É o padrão.
  • Push CDN: você envia os arquivos para a CDN antes de alguém pedir. Faz sentido para arquivos grandes e previsíveis, como o lançamento de um episódio de série, em que você quer tudo nas bordas antes da estreia.

Versionamento de URL, em detalhe

Invalidar uma CDN é lento (pode levar minutos para chegar a todos os PoPs) e às vezes cobrado. O truque é nunca precisar invalidar: o nome do arquivo inclui um hash do conteúdo (app.3f9a1c.js), com TTL de 1 ano. Quando o arquivo muda, o hash muda, o HTML aponta para o novo nome, e o antigo simplesmente deixa de ser pedido. Só o HTML, que é pequeno, fica com TTL curto.

CDN para conteúdo dinâmico

Mesmo respostas que não podem ser cacheadas se beneficiam de passar pela CDN: o usuário termina TCP+TLS no PoP próximo (RTT curto), e o PoP fala com a origem por conexões já abertas e rotas otimizadas. Respostas públicas e iguais para todos (a home de um portal de notícias) podem ser cacheadas por poucos segundos, o que já corta a maior parte da carga num pico.

Passo 7: camada web stateless

Se a sessão do usuário fica na memória do servidor A, toda requisição dele precisa ir ao A (sticky sessions), o que atrapalha o balanceamento e impede derrubar servidores. A solução é tirar o estado da camada web e colocá-lo num store compartilhado (Redis, DynamoDB, banco) ou num token assinado (JWT).

Com servidores stateless, o autoscaling fica trivial: adicione ou remova servidores conforme CPU ou fila de requisições, sem perder sessões.

Store de sessão × token assinado (JWT)

Sessão no Redis
  • O cliente guarda só um ID aleatório.
  • Logout e revogação são imediatos: apague a chave.
  • Custa uma ida ao Redis por requisição, e o Redis precisa ser altamente disponível.
JWT
  • O token carrega os dados (user_id, papéis, expiração) assinados pelo servidor; qualquer servidor valida sem consultar nada.
  • Revogar é difícil: o token vale até expirar. Por isso se usa token de acesso curto (5–15 min) + refresh token guardado no servidor.
  • Tokens grandes vão em toda requisição.

Autoscaling na prática

  • Métrica: CPU média é a mais comum; para serviços limitados por I/O, use requisições em andamento ou latência. Para workers, use o tamanho da fila.
  • Tempo de reação: uma máquina nova leva de 30 s (container) a alguns minutos (VM) para ficar pronta. O autoscaling não salva você de um pico que chega em segundos; para isso, mantenha folga (por exemplo, escalar quando a CPU passar de 50–60%, não de 90%) ou pré-escale antes de eventos conhecidos.
  • Escalar para baixo devagar: reduza capacidade com calma para não oscilar (sobe, desce, sobe).

Passo 8: múltiplos data centers

Para disponibilidade e latência global, os usuários são roteados por GeoDNS para o data center mais próximo (por exemplo, 70% US-East, 30% EU-West). Se um DC cai, todo o tráfego vai para o outro.

Desafios técnicos:

  • Redirecionamento de tráfego: GeoDNS ou anycast.
  • Sincronização de dados: cada região tem seu banco; num failover, o outro DC precisa ter os dados. Replicação assíncrona entre regiões (Netflix faz isso) traz consistência eventual e conflitos.
  • Teste e deploy: automação para manter os DCs idênticos e testar a aplicação em várias regiões.

Dois números definem o quanto investir: RTO (Recovery Time Objective, quanto tempo fora do ar é aceitável) e RPO (Recovery Point Objective, quantos segundos de dados você aceita perder). Um RPO de zero exige replicação síncrona entre regiões, o que adiciona dezenas de milissegundos a cada escrita. Pergunte esses números ao entrevistador em vez de assumir "zero perda, zero indisponibilidade".

Passo 9: fila de mensagens

Uma fila é um buffer durável que desacopla produtores e consumidores. O produtor publica e segue a vida; consumidores processam no seu ritmo. Exemplo: um upload de foto publica "processar foto" e workers aplicam filtros e geram miniaturas. Se a fila cresce, adicionamos workers; se esvazia, removemos.

Exemplo: processamento de fotos

Benefícios: tolerância a picos, isolamento de falhas (o consumidor caiu? as mensagens esperam), escala independente, retries. Kafka × RabbitMQ × SQS está em Ferramentas.

O que você precisa saber sobre filas

  • Garantia de entrega. Quase todas as filas oferecem at-least-once: se o worker processa a mensagem e morre antes de confirmar (ack), ela é entregue de novo. Logo, o processamento precisa ser idempotente: processar duas vezes tem o mesmo efeito que uma. A técnica comum é guardar o ID da mensagem já processada (ou usar uma chave única no banco) e ignorar repetições. Exactly-once de ponta a ponta praticamente não existe; o que existe é at-least-once + idempotência.
  • Visibility timeout. No SQS, quando um worker pega uma mensagem, ela fica invisível por X segundos. Se não houver ack nesse tempo, ela volta para a fila. X precisa ser maior que o tempo de processamento, senão dois workers processam a mesma mensagem.
  • Retries e DLQ. Mensagens que falham repetidamente (dado inválido, bug) não podem ficar voltando para sempre e bloqueando a fila. Depois de N tentativas, vão para uma dead-letter queue, onde alguém investiga.
  • Ordem. Filas comuns não garantem ordem entre mensagens. Se a ordem importa (eventos da mesma conta), use partições por chave (Kafka) ou filas FIFO com group ID.
  • Backpressure. A fila absorve picos, mas não cria capacidade. Se a taxa de chegada fica acima da taxa de processamento por muito tempo, a fila cresce sem parar. Monitore a idade da mensagem mais antiga, não só o tamanho da fila.
Quando usar fila (e quando não) Use quando o usuário não precisa do resultado na hora: enviar e-mail, gerar miniaturas, processar pagamento já autorizado, atualizar índices de busca. Não use quando a resposta depende do resultado: validar senha no login não vai para uma fila. Uma pergunta útil: "se esse passo atrasar 30 segundos, alguém percebe?"

Passo 10: logs, métricas e automação

  • Logs centralizados (ELK/Loki/CloudWatch) para investigar erros.
  • Métricas de host (CPU, memória, disco), agregadas (latência do banco, hit rate do cache) e de negócio (DAU, retenção, receita).
  • Tracing distribuído (OpenTelemetry) para seguir uma requisição entre serviços.
  • CI/CD para builds, testes e deploys automatizados.

O que monitorar: os quatro sinais de ouro

Para cada serviço, quatro métricas respondem "está saudável?":

  1. Latência: use percentis (p50, p95, p99), não média. Uma média de 50 ms pode esconder 1% de requisições levando 3 s, e se uma página faz 100 chamadas, quase todo usuário encontra uma dessas.
  2. Tráfego: requisições por segundo.
  3. Erros: taxa de 5xx e de respostas erradas.
  4. Saturação: quão perto do limite (CPU, memória, conexões do banco, tamanho de fila).

Sobre isso se definem SLIs (o que medir, por exemplo "% de requisições abaixo de 300 ms"), SLOs (a meta interna: 99,9% num mês) e SLAs (o contrato com o cliente, com multa). 99,9% de disponibilidade permite ~43 minutos fora do ar por mês; 99,99% permite ~4 minutos.

Passo 11: sharding do banco

Quando nem o maior servidor dá conta das escritas ou do volume de dados, dividimos o banco em shards: bancos com o mesmo esquema e dados diferentes. A sharding key decide onde cada linha mora, por exemplo user_id % 4.

A escolha mais importante é a sharding key: ela deve distribuir os dados de maneira uniforme e permitir que a maioria das queries vá a um único shard.

ProblemaExplicaçãoMitigação
ReshardingUm shard enche ou cresce de modo desigual; % N muda quase tudo de lugar quando N muda.Consistent hashing ou shards lógicos (muitas partições virtuais mapeadas a poucos nós).
Celebridade (hotspot)Um shard recebe tráfego desproporcional (o perfil de uma celebridade).Shard dedicado, subparticionar a chave, cache.
Joins e desnormalizaçãoJoins entre shards são caros ou inviáveis.Desnormalizar para responder por um único shard.
Transações entre shardsExigem 2PC ou sagas.Modelar para que as transações fiquem em um shard.

Exemplo: escolhendo a sharding key de um e-commerce

  • order_id: distribui bem, mas "listar os pedidos do usuário 42" precisa consultar todos os shards.
  • user_id: todos os pedidos de um usuário ficam juntos, então a tela "meus pedidos" é uma consulta num shard só, e uma transação que mexe nos dados de um único usuário também. Distribui bem se nenhum usuário for gigante. Geralmente é a melhor escolha.
  • created_at: péssima para escrita (todo pedido novo cai no mesmo shard).
  • E a visão do vendedor ("pedidos da minha loja")? Com shard por user_id, ela fica espalhada. A solução usual é um índice secundário global, uma segunda tabela particionada por seller_id, mantida de forma assíncrona (via eventos/CDC), aceitando um pequeno atraso.

Resharding sem dor: shards lógicos

Em vez de hash % 4 com 4 servidores, crie de início muitos shards lógicos (por exemplo, 1.024) com hash % 1024 e mapeie vários shards lógicos para cada servidor físico (256 por servidor). Para adicionar um servidor, você move alguns shards lógicos inteiros para ele; a função de hash nunca muda, só a tabela "shard lógico → servidor". É o que fazem Vitess, Citus e a maioria dos sistemas em produção. Consistent hashing (capítulo 05) resolve o mesmo problema de outro jeito.

Na entrevista Não proponha sharding cedo. Mostre com números que um único primário (com réplicas e cache) não aguenta, seja pelas escritas por segundo, seja pelo volume em TB, e só então escolha a chave justificando pelos padrões de acesso.

A arquitetura final

Resumo: como escalar para milhões de usuários
  • Camada web stateless.
  • Redundância em todos os níveis.
  • Cache em tudo o que for possível.
  • Múltiplos data centers.
  • Estáticos na CDN.
  • Dados escalados por sharding.
  • Camadas divididas em serviços independentes.
  • Monitoramento e automação.

Erros comuns

  • Começar pelo fim. Desenhar Kafka, sharding e microsserviços para um sistema de 10 mil usuários. Comece simples e evolua conforme os números.
  • Esquecer redundância em uma camada. Três servidores web, mas um único Redis sem réplica: o sistema é tão disponível quanto a peça menos redundante.
  • Cache sem TTL e sem plano para quando ele cai.
  • Ler de réplica logo depois de escrever sem pensar em atraso de replicação.
  • Tratar a fila como mágica. Esquecer idempotência, DLQ e o que acontece se o consumidor ficar para trás.
  • Escolher a sharding key sem olhar as queries.

Simulação: "Nosso app vai crescer 100×. O que você muda?"

Temos um app de receitas num único servidor com Postgres. Vamos aparecer num programa de TV e esperamos 100× mais tráfego em 3 semanas. Como você prepararia a arquitetura?

Antes de propor algo, quero entender o perfil. Quantos usuários ativos hoje, e qual a proporção de leitura e escrita? Imagino que a maioria só veja receitas.

Uns 20 mil DAU hoje. Sim, 95% é leitura de receitas e fotos; escritas são comentários e favoritos.

Ótimo, então o problema é principalmente de leitura. Eu atacaria em ordem de impacto por esforço. Primeiro, fotos e assets estáticos numa CDN, com origem no S3: provavelmente é a maior parte dos bytes e sai do servidor de uma vez. Segundo, tornaria a aplicação stateless, com sessões no Redis ou JWT, e colocaria 2+ instâncias atrás de um load balancer com autoscaling. Isso também elimina o ponto único de falha.

E o banco?

Separado num serviço gerenciado com 1 primário e 2 réplicas de leitura. As páginas de receita, que são quase imutáveis, iriam para um cache Redis com TTL de alguns minutos via cache-aside. Com 95% de leitura, espero um hit rate acima de 90%, então o banco recebe uma fração pequena do tráfego.

Um pico de TV é bem concentrado: todo mundo entra no mesmo minuto na mesma receita.

Esse é o caso de thundering herd numa chave quente. Eu faria pré-aquecimento do cache com as receitas que vão aparecer no programa, e no código usaria single-flight para que só uma requisição recarregue a chave expirada. Também colocaria a própria página dessa receita em cache na CDN por 30–60 s. E faria um teste de carga simulando 100× antes do programa.

Precisa de sharding?

Não agora. 100× de 20 mil DAU são 2 milhões. Mesmo que cada usuário faça 10 escritas por dia, são ~230 escritas/s no pico, que um Postgres bem dimensionado aguenta tranquilamente. Sharding traz muita complexidade; eu só consideraria se os números de escrita ou o volume de dados pedissem.

O que a entrevistadora quer ver: perguntas sobre o perfil de tráfego, priorização por impacto, números para justificar o que não fazer, e atenção a picos concentrados.

Quiz

Por que tornar a camada web stateless?
Sem estado local, servidores viram peças intercambiáveis: dá para adicionar, remover ou perder um sem afetar sessões.
Um usuário atualiza o perfil e, ao recarregar, vê o dado antigo. Causa mais provável?
Replicação assíncrona causa esse sintoma. A solução é read-your-writes: ler do primário logo após a própria escrita.
Qual é o principal problema de usar hash(key) % N para escolher o shard?
De 4 para 5 shards, cerca de 80% das chaves mudam de lugar. Consistent hashing move só ~1/N.
Quando um cache NÃO é uma boa ideia?
Se o dado muda a cada leitura, o cache vive sendo invalidado: custo sem benefício.
