Projete um rate limiter

Limitar quantas requisições um cliente pode fazer num intervalo. Parece simples, mas envolve algoritmos, estado distribuído, condições de corrida e onde colocar o componente.

Ao final você saberá:

  • Comparar os 5 algoritmos (token bucket, leaking bucket, fixed window, sliding log, sliding counter).
  • Projetar um rate limiter distribuído com Redis, sem race conditions.
  • Decidir onde colocá-lo (cliente, API gateway, middleware, serviço).
  • Implementar todos os algoritmos em Go.

Por que rate limiting?

  • Evitar abuso e DoS, intencional ou acidental (um cliente com bug em loop).
  • Reduzir custo: chamadas a APIs pagas de terceiros (pagamento, SMS, LLM).
  • Proteger servidores de sobrecarga e garantir justiça entre clientes (planos free × pro).

Passo 1: requisitos

É um rate limiter do lado do cliente ou do servidor?

Servidor, para a nossa API.

Limitamos por IP, por usuário ou por outro critério?

Deve ser flexível para suportar regras diferentes.

Qual a escala?

Uma startup grande, com milhões de usuários.

Funciona num ambiente distribuído, com vários servidores?

Sim.

Serviço separado ou parte do código da aplicação?

Você decide.

Avisamos o usuário quando ele é limitado?

Sim.

  • Limitar requisições com precisão, com baixa latência (não pode deixar a API lenta).
  • Usar pouca memória.
  • Limite distribuído, compartilhado entre servidores.
  • Tratamento de exceções: resposta clara (HTTP 429).
  • Tolerância a falhas: se o rate limiter cair, o sistema continua funcionando (fail-open).

Os algoritmos

1. Token bucket

Um balde de capacidade C é reabastecido a r tokens/s. Cada requisição consome um token; sem token, recebe 429. Dois parâmetros: tamanho do balde e taxa de reposição.

Prós
  • Fácil de implementar, pouca memória
  • Permite rajadas curtas (até C), o que é bom para uso humano
Contras
  • Ajustar 2 parâmetros não é trivial

Usado por Amazon e Stripe. Quantos baldes? Um por endpoint e por usuário (por exemplo, 1 post/s e 150 likes/dia), um por IP, ou um global (10 mil req/s no sistema).

go/ratelimit/tokenbucket.go
package ratelimit

import (
	"sync"
	"time"
)

// TokenBucket: cada chave tem um balde com capacidade `capacity`.
// Tokens são repostos continuamente a `refillPerSec` tokens/segundo.
// Cada requisição consome 1 token; sem token, a requisição é rejeitada.
//
// Permite rajadas (burst) de até `capacity` requisições — é o algoritmo
// usado por Amazon API Gateway e Stripe.
type TokenBucket struct {
	mu           sync.Mutex
	capacity     float64
	refillPerSec float64
	now          Clock
	buckets      map[string]*bucket
}

type bucket struct {
	tokens   float64
	lastSeen time.Time
}

func NewTokenBucket(capacity int, refillPerSec float64, now Clock) *TokenBucket {
	if now == nil {
		now = time.Now
	}
	return &TokenBucket{
		capacity:     float64(capacity),
		refillPerSec: refillPerSec,
		now:          now,
		buckets:      make(map[string]*bucket),
	}
}

func (tb *TokenBucket) Allow(key string) bool {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	now := tb.now()
	b, ok := tb.buckets[key]
	if !ok {
		// Balde novo começa cheio.
		b = &bucket{tokens: tb.capacity, lastSeen: now}
		tb.buckets[key] = b
	}

	// Refill "preguiçoso": em vez de um timer por balde, calculamos
	// quantos tokens teriam entrado desde a última visita.
	elapsed := now.Sub(b.lastSeen).Seconds()
	b.tokens = min(tb.capacity, b.tokens+elapsed*tb.refillPerSec)
	b.lastSeen = now

	if b.tokens >= 1 {
		b.tokens--
		return true
	}
	return false
}

2. Leaking bucket

Requisições entram numa fila FIFO de tamanho fixo e são processadas a uma taxa constante. Fila cheia: descarta.

Prós
  • Saída estável: bom quando o backend precisa de vazão constante
  • Memória limitada
Contras
  • Uma rajada enche a fila com requisições antigas, e as novas são descartadas
  • 2 parâmetros para ajustar

Usado pela Shopify.

go/ratelimit/leakybucket.go
package ratelimit

import (
	"sync"
	"time"
)

// LeakyBucket (leaking bucket): requisições entram numa fila de tamanho fixo
// e "vazam" (são processadas) a uma taxa constante. Suaviza o tráfego:
// a saída é estável mesmo com entrada em rajadas. Usado pela Shopify.
//
// Aqui modelamos apenas a decisão de admissão: o "nível de água" cai
// `leakPerSec` por segundo; se a fila está cheia, rejeitamos.
type LeakyBucket struct {
	mu         sync.Mutex
	queueSize  float64
	leakPerSec float64
	now        Clock
	levels     map[string]*level
}

type level struct {
	water    float64
	lastLeak time.Time
}

func NewLeakyBucket(queueSize int, leakPerSec float64, now Clock) *LeakyBucket {
	if now == nil {
		now = time.Now
	}
	return &LeakyBucket{queueSize: float64(queueSize), leakPerSec: leakPerSec, now: now, levels: map[string]*level{}}
}

func (lb *LeakyBucket) Allow(key string) bool {
	lb.mu.Lock()
	defer lb.mu.Unlock()

	now := lb.now()
	l, ok := lb.levels[key]
	if !ok {
		l = &level{lastLeak: now}
		lb.levels[key] = l
	}
	leaked := now.Sub(l.lastLeak).Seconds() * lb.leakPerSec
	l.water = max(0, l.water-leaked)
	l.lastLeak = now

	if l.water+1 <= lb.queueSize {
		l.water++
		return true
	}
	return false
}

3. Fixed window counter

A linha do tempo é dividida em janelas fixas (por exemplo, por minuto), com um contador por janela. Passou do limite, rejeita até a próxima janela.

Prós
  • Simplíssimo (INCR + EXPIRE)
  • Pouca memória
Contras
  • Pico na borda: com limite de 5/min, 5 requisições em 12:00:59 e mais 5 em 12:01:00 fazem 10 em 1 segundo

4. Sliding window log

Guarda o timestamp de cada requisição (em Redis, um sorted set). A cada requisição, remove os timestamps mais antigos que a janela e conta os restantes.

Prós
  • Preciso em qualquer janela móvel
Contras
  • Muita memória: guarda timestamps até das requisições rejeitadas (na versão clássica) ou de todas as aceitas

5. Sliding window counter

Híbrido: usa os contadores da janela atual e da anterior e estima a contagem da janela móvel:

requisições na janela móvel ≈ atual + anterior × (% da janela anterior que ainda está dentro da janela móvel)

Ex.: limite 7/min; janela anterior teve 5; atual tem 3; estamos a 30% da janela atual
     3 + 5 × 0,7 = 6,5 → arredonda para 6 → cabe mais 1
Prós
  • Suaviza os picos de borda
  • Memória O(1)
Contras
  • Aproximado: assume tráfego uniforme na janela anterior. Segundo a Cloudflare, apenas ~0,003% das requisições foram aceitas ou rejeitadas de forma errada em 400 milhões
go/ratelimit/window.go: fixed window, sliding log e sliding counter
package ratelimit

import (
	"sync"
	"time"
)

// ---------------------------------------------------------------------------
// Fixed window counter
// ---------------------------------------------------------------------------

// FixedWindow conta requisições em janelas alinhadas (ex.: 12:00:00–12:00:59).
// Simples e barato (1 contador por chave), mas tem o problema da borda:
// `limit` requisições no fim de uma janela + `limit` no início da próxima
// = 2×limit dentro de um intervalo de `window`.
type FixedWindow struct {
	mu       sync.Mutex
	limit    int
	window   time.Duration
	now      Clock
	counters map[string]*fwCounter
}

type fwCounter struct {
	windowStart time.Time
	count       int
}

func NewFixedWindow(limit int, window time.Duration, now Clock) *FixedWindow {
	if now == nil {
		now = time.Now
	}
	return &FixedWindow{limit: limit, window: window, now: now, counters: map[string]*fwCounter{}}
}

func (fw *FixedWindow) Allow(key string) bool {
	fw.mu.Lock()
	defer fw.mu.Unlock()

	now := fw.now()
	start := now.Truncate(fw.window) // início da janela atual
	c, ok := fw.counters[key]
	if !ok || !c.windowStart.Equal(start) {
		c = &fwCounter{windowStart: start}
		fw.counters[key] = c
	}
	if c.count < fw.limit {
		c.count++
		return true
	}
	return false
}

// ---------------------------------------------------------------------------
// Sliding window log
// ---------------------------------------------------------------------------

// SlidingWindowLog guarda o timestamp de cada requisição aceita (em Redis seria
// um sorted set). Preciso — nunca passa do limite em nenhuma janela móvel —
// porém consome memória O(limit) por chave.
type SlidingWindowLog struct {
	mu     sync.Mutex
	limit  int
	window time.Duration
	now    Clock
	logs   map[string][]time.Time
}

func NewSlidingWindowLog(limit int, window time.Duration, now Clock) *SlidingWindowLog {
	if now == nil {
		now = time.Now
	}
	return &SlidingWindowLog{limit: limit, window: window, now: now, logs: map[string][]time.Time{}}
}

func (sl *SlidingWindowLog) Allow(key string) bool {
	sl.mu.Lock()
	defer sl.mu.Unlock()

	now := sl.now()
	cutoff := now.Add(-sl.window)
	log := sl.logs[key]

	// Remove timestamps fora da janela (ZREMRANGEBYSCORE no Redis).
	i := 0
	for i < len(log) && !log[i].After(cutoff) {
		i++
	}
	log = log[i:]

	if len(log) < sl.limit {
		sl.logs[key] = append(log, now)
		return true
	}
	sl.logs[key] = log
	return false
}

// ---------------------------------------------------------------------------
// Sliding window counter
// ---------------------------------------------------------------------------

// SlidingWindowCounter é o meio-termo: guarda só 2 contadores (janela atual e
// anterior) e estima a contagem da janela móvel por média ponderada:
//
//	estimativa = atual + anterior × (fração da janela anterior ainda coberta)
//
// Memória O(1) por chave; erro pequeno (assume tráfego uniforme na janela anterior).
type SlidingWindowCounter struct {
	mu     sync.Mutex
	limit  int
	window time.Duration
	now    Clock
	state  map[string]*swState
}

type swState struct {
	currStart time.Time
	curr      int
	prev      int
}

func NewSlidingWindowCounter(limit int, window time.Duration, now Clock) *SlidingWindowCounter {
	if now == nil {
		now = time.Now
	}
	return &SlidingWindowCounter{limit: limit, window: window, now: now, state: map[string]*swState{}}
}

func (sc *SlidingWindowCounter) Allow(key string) bool {
	sc.mu.Lock()
	defer sc.mu.Unlock()

	now := sc.now()
	start := now.Truncate(sc.window)
	s, ok := sc.state[key]
	switch {
	case !ok:
		s = &swState{currStart: start}
		sc.state[key] = s
	case start.Sub(s.currStart) == sc.window: // avançou exatamente uma janela
		s.prev, s.curr, s.currStart = s.curr, 0, start
	case start.Sub(s.currStart) > sc.window: // ficou mais de uma janela sem tráfego
		s.prev, s.curr, s.currStart = 0, 0, start
	}

	elapsed := now.Sub(s.currStart).Seconds() / sc.window.Seconds()
	estimate := float64(s.curr) + float64(s.prev)*(1-elapsed)
	if estimate+1 <= float64(sc.limit) {
		s.curr++
		return true
	}
	return false
}

Arquitetura de alto nível

Onde guardar os contadores? Banco é lento demais (disco). Use Redis: em memória, com INCR atômico e EXPIRE.

Resposta ao cliente

HTTP/1.1 429 Too Many Requests
X-Ratelimit-Limit: 100
X-Ratelimit-Remaining: 0
X-Ratelimit-Reset: 1735689600      (ou Retry-After: 30)

Requisições rejeitadas podem ser descartadas ou enfileiradas para processamento posterior (por exemplo, pedidos que não devem ser perdidos).

go/ratelimit/middleware.go
package ratelimit

import (
	"net"
	"net/http"
)

// Middleware aplica um Limiter a um http.Handler, usando o IP do cliente
// como chave. Ao rejeitar, responde 429 Too Many Requests com o header
// Retry-After — o cliente sabe que deve esperar em vez de repetir em loop.
func Middleware(l Limiter, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key, _, err := net.SplitHostPort(r.RemoteAddr)
		if err != nil {
			key = r.RemoteAddr
		}
		if !l.Allow(key) {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "rate limit exceeded", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}

Deep dive: rate limiter distribuído

Race condition

"Ler contador → checar → escrever contador+1" em duas requisições concorrentes: as duas leem 3, as duas escrevem 4, e uma requisição escapa do limite.

  • Locks resolvem, mas são lentos.
  • Lua script no Redis torna a operação atômica (o Redis executa scripts de forma serial):
-- Token bucket atômico no Redis. KEYS[1]=chave  ARGV: capacidade, taxa/s, agora(ms)
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return allowed

Para sliding log: MULTI com ZREMRANGEBYSCORE + ZADD + ZCARD + EXPIRE.

Sincronização entre vários rate limiters

Com vários nós de middleware, o estado não pode ficar em memória local (o cliente 1 vai ao nó A, o cliente 2 ao nó B…). Sticky sessions não escalam. Solução: store centralizado (Redis). Para reduzir a latência, um meio-termo é manter contadores locais e sincronizar com o Redis em lotes, aceitando uma pequena imprecisão.

Otimizações e escala

  • Multi-DC: edge servers ao redor do mundo (Cloudflare tem centenas de PoPs) e sincronização eventual entre regiões.
  • Redis Cluster particionado pela chave do cliente.
  • Fail-open × fail-closed: se o Redis cair, deixa passar (disponibilidade) ou bloqueia (proteção)? Para a API geral, fail-open; para login e anti-fraude, talvez fail-closed.
  • Monitoramento: taxa de 429 por regra. Muito alta pode significar regra rígida demais; durante um pico legítimo (flash sale), o algoritmo pode precisar permitir rajadas (token bucket).

Outras camadas

Rate limiting pode ser aplicado também na camada de rede (L3, com iptables por IP) ou de transporte. No cliente: cache, evitar chamadas em loop, retry com backoff exponencial e respeito ao Retry-After.

Simulação de entrevista

Vamos projetar um rate limiter para a API pública de uma plataforma de pagamentos. Por onde começa?

Algumas perguntas. A chave do limite é a API key do comerciante? Há limites diferentes por plano e por endpoint, por exemplo criar cobrança × consultar? Qual o volume total?

Por API key, com limites por plano e por endpoint. Uns 50 mil req/s no total, picos de 3× na Black Friday.

Então vou de token bucket. Comerciantes legítimos têm rajadas (um lote de cobranças no fim do dia), e o token bucket permite isso até a capacidade do balde mantendo a taxa média. O estado fica no Redis Cluster com a chave rl:{api_key}:{endpoint}, e a atualização é um script Lua atômico para evitar race conditions entre instâncias do gateway.

50 mil req/s indo ao Redis não adiciona latência?

Uma ida ao Redis no mesmo DC custa ~0,5 ms, o que é aceitável. São 150 mil ops/s no pico, distribuídas pelo cluster com alguns shards. Se a latência fosse crítica, poderia usar um token bucket local em cada gateway, com uma fração do limite, e sincronizar periodicamente. Perde-se precisão, mas é viável.

E se o Redis cair?

Para uma API de pagamentos eu faria fail-open com um limite local conservador em memória. Bloquear todas as cobranças por uma falha do rate limiter seria pior para o negócio que deixar passar um excesso temporário. Isso vem com alerta imediato, e o Redis teria réplicas com failover automático.

Como o cliente sabe quando tentar de novo?

Respondo 429 com Retry-After e os headers X-RateLimit-Limit/Remaining/Reset, para o SDK implementar backoff. E, como é pagamento, os retries precisam usar idempotency key, para que repetir uma cobrança limitada não gere duplicata.

Perguntas de follow-up comuns

Como limitar um usuário em vários datacenters?

Opções: (1) limite por região (cada DC aplica limite/N, simples mas impreciso se o tráfego se concentrar); (2) contadores locais com sincronização assíncrona entre regiões (eventual, permite pequenos excessos); (3) store global consistente (preciso, mas adiciona latência cross-region, o que raramente vale a pena). A maioria escolhe (1) ou (2).

Como proteger contra hot keys no Redis (um cliente gigante)?

Dividir o limite em N sub-chaves (key#0..N, cada uma com limite/N, escolhendo aleatoriamente) ou aplicar um pré-filtro local no gateway.

Rate limiting × throttling × load shedding?

Rate limiting: limite por cliente (justiça e abuso). Throttling: desacelerar (atrasar ou enfileirar) em vez de rejeitar. Load shedding: proteger o servidor rejeitando tráfego quando ele está sobrecarregado, independentemente do cliente.

Como limitar por concorrência em vez de taxa?

Um semáforo distribuído: contador de requisições em andamento (INCR na entrada, DECR na saída, com TTL para não vazar se o processo morrer). Útil para endpoints caros como relatórios e chamadas a LLMs.

Quiz

Qual algoritmo permite rajadas controladas mantendo uma taxa média?
Tokens acumulados até C permitem rajadas; a reposição a r/s controla a média.
Limite de 100/min com fixed window. Quantas requisições podem passar, no pior caso, em 2 segundos?
100 no último segundo de uma janela + 100 no primeiro da próxima.
Como evitar a race condition "ler, checar, incrementar" no Redis?
O Redis executa scripts atomicamente: nenhuma outra operação intercala.
Que código HTTP indica que o cliente foi limitado?
429 Too Many Requests, idealmente com Retry-After.
