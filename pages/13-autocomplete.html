Projete o autocomplete de uma busca

"Typeahead": a cada tecla, as 5 sugestões mais populares que começam com o que você digitou, em menos de 100 ms. O problema tem duas metades: servir rápido (trie) e manter os dados atualizados (pipeline).

Ao final você saberá:

  • Estimar o tráfego gerado "a cada tecla".
  • Usar uma trie com top-k cacheado em cada nó.
  • Montar o pipeline de coleta e agregação de dados.
  • Escalar a trie (sharding por prefixo) e otimizar com cache no navegador.

Requisitos

O casamento é só no início (prefixo) ou também no meio?

Só no início.

Quantas sugestões?

5.

Como escolher as 5?

Por popularidade (frequência histórica de busca).

Corretor ortográfico?

Não.

Idioma?

Inglês; multilíngue se der tempo.

Maiúsculas e caracteres especiais?

Tudo minúsculo e alfabético.

Escala?

10 milhões de DAU.

  • Rapidez: menos de 100 ms (senão a experiência engasga).
  • Relevância e ordenação por popularidade.
  • Escalabilidade e alta disponibilidade.

Estimativas

  • 10 M DAU × 10 buscas/dia × 20 caracteres (uma requisição por tecla) = 2 bilhões de requisições/dia, ou ~24.000 QPS; pico ~48.000.
  • Se 20% das buscas são novas: 10 M × 10 × 20 B × 20% = 0,4 GB/dia de dados novos.

Alto nível

Serviço de coleta (registra consultas e frequências) e serviço de consulta (devolve o top 5 de um prefixo). A versão ingênua, uma tabela (query, frequency) com

SELECT query FROM frequency_table WHERE query LIKE 'tw%' ORDER BY frequency DESC LIMIT 5;

funciona com pouco dado, mas é lenta em escala. Daí a trie.

Deep dive: a trie

Árvore em que cada nó é um caractere; o caminho da raiz até um nó forma um prefixo. Cada nó terminal guarda a frequência da consulta completa.

Busca ingênua de top-k: (1) achar o nó do prefixo, O(p); (2) percorrer a subárvore para achar todos os termos, O(c); (3) ordenar, O(c log c). Com prefixos curtos (uma letra), c é enorme.

Duas otimizações:

  1. Limitar o tamanho do prefixo: ninguém digita 200 caracteres; p ≤ 50 faz o passo 1 virar O(1).
  2. Cachear o top-k em cada nó: cada nó guarda suas 5 consultas mais frequentes. A consulta vira O(1) (descer até o nó e ler a lista). O custo é memória extra, troca que vale muito a pena.
go/autocomplete/trie.go
// Package autocomplete implementa uma trie com top-k pré-computado em cada nó.
//
// Busca ingênua: achar o nó do prefixo (O(p)) e percorrer toda a subárvore
// para encontrar as k consultas mais frequentes — lento para prefixos curtos.
// Otimização clássica: cada nó guarda os seus top-k. A consulta vira O(p),
// em troca de mais memória e de uma reconstrução periódica (offline, ex.: semanal)
// a partir dos logs agregados de busca.
package autocomplete

import (
	"sort"
	"strings"
)

type Suggestion struct {
	Query string
	Freq  int
}

type node struct {
	children map[rune]*node
	top      []Suggestion
}

type Trie struct {
	root *node
	k    int
}

func NewTrie(k int) *Trie { return &Trie{root: &node{children: map[rune]*node{}}, k: k} }

// Build constrói a trie a partir de frequências agregadas (saída do job de analytics).
func Build(freq map[string]int, k int) *Trie {
	t := NewTrie(k)
	for q, f := range freq {
		t.insert(strings.ToLower(q), f)
	}
	return t
}

func (t *Trie) insert(q string, f int) {
	s := Suggestion{q, f}
	n := t.root
	t.offer(n, s)
	for _, r := range q {
		child, ok := n.children[r]
		if !ok {
			child = &node{children: map[rune]*node{}}
			n.children[r] = child
		}
		n = child
		t.offer(n, s)
	}
}

// offer mantém em cada nó apenas os k melhores.
func (t *Trie) offer(n *node, s Suggestion) {
	n.top = append(n.top, s)
	sort.Slice(n.top, func(i, j int) bool {
		if n.top[i].Freq != n.top[j].Freq {
			return n.top[i].Freq > n.top[j].Freq
		}
		return n.top[i].Query < n.top[j].Query
	})
	if len(n.top) > t.k {
		n.top = n.top[:t.k]
	}
}

// Suggest é O(len(prefix)): desce até o nó e devolve o top-k cacheado.
func (t *Trie) Suggest(prefix string) []Suggestion {
	n := t.root
	for _, r := range strings.ToLower(prefix) {
		next, ok := n.children[r]
		if !ok {
			return nil
		}
		n = next
	}
	return n.top
}

Deep dive: pipeline de coleta

Atualizar a trie a cada busca (bilhões por dia) seria lento e desnecessário: o top 5 muda pouco. Em vez disso:

  • Logs crus, append-only, não indexados.
  • Agregação com periodicidade conforme o caso: Google pode precisar de tempo real (tendências), mas para muitos casos semanal basta.
  • Workers constroem a trie de forma assíncrona e salvam no Trie DB: (a) documento serializado (MongoDB) ou (b) KV com prefixo → top-k (cada nó vira uma linha), o que facilita o sharding.
  • Trie cache: a trie em memória distribuída, recarregada a cada snapshot semanal.

Serviço de consulta

  1. Requisição chega ao LB e vai aos servidores de API.
  2. Busca no trie cache; num miss, busca no trie DB e repopula o cache.

Otimizações:

  • AJAX sem recarregar a página.
  • Cache no navegador: as sugestões mudam pouco. O Google responde com Cache-Control: private, max-age=3600.
  • Debounce no cliente: só envia depois de ~100–150 ms sem digitar.
  • Amostragem de logs: registrar 1 de cada N buscas, porque a popularidade sobrevive à amostragem.

Manutenção da trie

  • Criar: pelos workers, a partir dos dados agregados.
  • Atualizar: reconstruir semanalmente e trocar a antiga (preferível), ou atualizar nós individuais, o que é lento porque o top-k dos ancestrais muda junto.
  • Remover sugestões: conteúdo ofensivo, violento ou perigoso. Uma camada de filtro na frente do cache remove na hora; a remoção física acontece no próximo rebuild.

Escalando o armazenamento

Sharding pela primeira letra (26 shards), depois pela segunda (aa–ag, ah–an…). Problema: a distribuição é desigual, porque há muito mais palavras com "s" do que com "x". Solução: um shard map manager que usa os dados históricos para combinar prefixos em shards de tamanho parecido (por exemplo, "s" sozinho num shard e "u–z" juntos em outro).

Fechamento e follow-ups

  • Multilíngue: nós com caracteres Unicode.
  • Por país: tries diferentes por região, em CDNs.
  • Tendências em tempo real (um evento quebra a internet): a reconstrução semanal não serve. Use streaming (Kafka + Flink) com janelas e pesos maiores para buscas recentes, mantendo uma trie "quente" pequena mesclada com a principal.
  • Personalização: mesclar o top global com o histórico do próprio usuário (no cliente ou num serviço separado).

Simulação de entrevista

Seu autocomplete atualiza semanalmente. Um terremoto acontece agora e todo mundo busca "terremoto em…". O que acontece?

No design semanal, o termo novo só apareceria na próxima reconstrução, o que é inaceitável para tendências. Eu adicionaria um caminho de tempo real: um consumidor de stream sobre os logs de busca conta as consultas em janelas de 5–10 minutos e mantém um top-k por prefixo para os termos em alta. O serviço de consulta mescla duas fontes: a trie histórica e esse índice de tendências, com o score da tendência ponderado por recência.

Contar todas as consultas em tempo real não fica caro?

Para heavy hitters não preciso de contagem exata: Count-Min Sketch + heap de top-k por janela, com memória fixa. Também amostro os logs. A precisão perdida é irrelevante para ranquear sugestões.

E como evitar que algo ofensivo vire tendência?

A camada de filtro na frente da resposta aplica uma blocklist com atualização imediata, e termos em alta passam por um classificador antes de entrar no índice de tendências. Há também um botão de remoção manual para casos urgentes.

Quiz

O que torna a consulta de top-k O(1) na trie?
Descer até o nó é limitado pelo tamanho do prefixo; a resposta já está pronta no nó.
Por que não atualizar a trie a cada busca?
Separe o caminho de escrita (pipeline batch/stream) do de leitura (cache em memória).
Por que sharding por primeira letra é problemático?
Daí o shard map manager baseado em dados históricos.
