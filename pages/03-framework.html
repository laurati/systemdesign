Capítulo 03 · Fundamentos

Um framework para a entrevista de system design

Quatro passos para não se perder em 45 minutos: entender o problema, propor o alto nível, aprofundar e fechar. Use em todo estudo de caso deste site.

Ao final você saberá:

  • Conduzir a entrevista com um roteiro previsível, mas flexível.
  • Distribuir o tempo entre as fases.
  • Fazer as perguntas de clarificação certas.
  • Evitar os erros que mais reprovam candidatos.

Conceitos deste capítulo

ConceitoDefinição
Requisitos funcionaisO que o sistema faz (publicar post, ver feed).
Requisitos não funcionaisComo ele precisa se comportar: escala, latência, disponibilidade, consistência, durabilidade.
Design de alto nívelVisão de ponta a ponta com os principais componentes e como os dados fluem entre eles.
Buy-inConcordância da pessoa entrevistadora com o rumo, antes de aprofundar.
Deep diveAprofundar um componente crítico, discutindo opções, trade-offs e falhas.
Trade-offGanhar algo abrindo mão de outra coisa (latência × consistência, custo × velocidade).
GargaloO componente que limita a capacidade do sistema inteiro.

Visão geral e tempo

O que está sendo avaliado

Entender o critério muda como você usa o tempo. Empresas grandes avaliam, com nomes diferentes, quatro coisas:

DimensãoO que eles observamSinal forteSinal fraco
Navegação do problemaVocê transforma um pedido vago em requisitos e prioridades?Corta escopo, pergunta escala e consistência, foca no que importaComeça a desenhar sem perguntar; tenta resolver tudo
Design de soluçãoO design funciona de ponta a ponta e atende aos requisitos?Componentes justificados, fluxos completos, dados bem modeladosCaixas soltas, fluxos que não fecham, tecnologia sem motivo
Profundidade técnicaVocê conhece os detalhes onde eles importam?Discute trade-offs concretos, falhas, númerosFica em "coloca um cache" sem dizer o quê, como e por quê
ComunicaçãoDá para trabalhar com você?Pensa em voz alta, checa alinhamento, aceita sugestõesSilêncio longo; defende uma ideia ruim; não escuta as dicas

O que muda com o nível

  • Pleno: esperam um design funcional e correto, com alguma profundidade quando provocado. Tudo bem a pessoa entrevistadora conduzir os deep dives.
  • Sênior: esperam que você conduza: escolha sozinho os pontos difíceis, antecipe falhas e gargalos e compare alternativas com trade-offs claros.
  • Staff+: além disso, visão de operação e evolução: custo, migração, como o sistema muda em 2 anos, o que você não construiria, e por quê.

Passo 1: entender o problema e definir o escopo

O erro número um é sair desenhando. Responder rápido não dá pontos extras: o sinal que conta é a capacidade de transformar um pedido vago em requisitos claros. Pergunte, escreva as respostas e, quando a pessoa entrevistadora devolver "o que você acha?", faça premissas razoáveis e anote.

Perguntas que funcionam em quase todo problema

CategoriaPerguntas
FuncionalidadesQuais são as 2 ou 3 funcionalidades mais importantes? O que está fora do escopo?
UsuáriosQuem usa? Quantos usuários (DAU/MAU)? Mobile, web ou os dois?
EscalaQual o crescimento esperado em 3, 6 ou 12 meses? Tráfego de leitura × escrita?
DadosQue tipo de dado (texto, imagem, vídeo)? Tamanho médio? Por quanto tempo guardar?
ConsistênciaPode ter atraso (consistência eventual) ou precisa ser imediato e exato (dinheiro, estoque)?
Latência e disponibilidadeQual latência aceitável? O sistema pode cair? É global?
ContextoHá infraestrutura existente que devo usar ou evitar? Cloud?

Saída do passo 1 (escreva no quadro)

Funcionais:
  - usuário publica post (texto + imagem)
  - usuário vê feed dos amigos, ordenado por tempo
  Fora do escopo: anúncios, busca, ranking por ML

Não funcionais:
  - 10M DAU, 5k amigos no máximo
  - leitura do feed < 200 ms (p99)
  - alta disponibilidade > consistência (eventual ok, até alguns segundos)

Estimativas: ~2k posts/s de pico, ~100k leituras de feed/s de pico
Requisitos não funcionais são o que define a arquitetura Os funcionais dizem o que o sistema faz; os não funcionais (escala, latência, disponibilidade, consistência, durabilidade) dizem como ele precisa ser construído. Deixe-os explícitos, porque você vai citá-los para justificar cada escolha: "como priorizamos disponibilidade, escolhi um store AP…".

Passo 2: propor o design de alto nível e obter buy-in

Objetivo: um desenho completo e simples que atenda a todos os requisitos funcionais. Trate a pessoa entrevistadora como colega de time.

  1. Defina as APIs (os contratos entre cliente e servidor): 
    POST /v1/posts            { content, media_ids[] }     → 201 { post_id }
GET  /v1/feed?cursor=…&limit=20                        → 200 { posts[], next_cursor }
  2. Desenhe os componentes: clientes, LB, serviços, bancos, cache, filas, CDN, object storage.
  3. Percorra os fluxos principais em cima do desenho: "quando o usuário publica, a requisição vai para…".
  4. Esboce o modelo de dados: entidades principais, chaves e qual banco.
  5. Faça as estimativas que importam para as escolhas (veja o capítulo 2).
  6. Peça buy-in: "isso cobre os requisitos? Faz sentido eu aprofundar em X?".

Como desenhar a API

  • Uma rota por requisito funcional. Se você listou 3 funcionalidades, devem existir pelo menos 3 rotas.
  • REST é o padrão seguro. Use WebSocket/SSE para push em tempo real (chat, notificações ao vivo) e gRPC para comunicação entre serviços internos.
  • O usuário vem do token de autenticação, nunca do corpo: POST /posts, não POST /posts {user_id}. Isso mostra cuidado com segurança.
  • Listas são paginadas. Prefira cursor (?cursor=<último id visto>) a offset: offset fica lento em páginas profundas e pula ou repete itens quando entram itens novos.
  • Operações que não podem ser duplicadas (pagamento, envio) aceitam uma idempotency key.

Como escolher o banco no modelo de dados

Para cada entidade, responda três perguntas e a escolha costuma sair sozinha:

  1. Como ela é lida? Por chave? Por intervalo? Com joins? Com busca textual?
  2. Quanto volume e quantas escritas? Cabe num primário ou precisa particionar?
  3. Que consistência precisa? Transação entre várias linhas (saldo, estoque) ou eventual?

Exemplo: usuários e seguidores (relações, volume moderado) → Postgres. Posts (muito volume, lidos por id ou por autor + tempo) → Cassandra/DynamoDB ou Postgres particionado. Fotos → S3. Feed pré-computado → Redis. Busca → Elasticsearch. Não tenha medo de usar mais de um banco, desde que cada um tenha um motivo. O guia completo está em Qual ferramenta usar?

Como percorrer os fluxos

Depois de desenhar, conte a história de uma requisição, numerando as setas: "1. o app chama POST /posts no LB; 2. o serviço de posts grava no banco; 3. publica um evento na fila; 4. o worker de fanout lê os seguidores e…". Fazer isso em voz alta revela buracos no seu desenho (de onde vem esse dado?) antes que a pessoa entrevistadora os encontre.

Não otimize cedo Não comece por sharding, Kafka e Kubernetes. Primeiro faça funcionar de ponta a ponta. Depois identifique os gargalos com base nos números e evolua. Mostrar essa evolução já é um sinal forte.

Passo 3: deep dive

Agora vocês concordaram com o alto nível. A pessoa entrevistadora pode escolher o foco ("me fale mais sobre o fanout") ou deixar com você. Escolha os componentes mais críticos ou mais difíceis do problema:

ProblemaDeep dives típicos
Encurtador de URLGeração do short code (hash × base62), colisões, cache, 301 × 302
ChatWebSocket e roteamento entre servidores, ordenação de mensagens, presença, multi-dispositivo
News feedFanout on write × on read, celebridades, cache
Rate limiterAlgoritmo, store distribuído, race conditions
YouTubePipeline de transcodificação, streaming adaptativo, custo de CDN
TicketmasterConcorrência em reservas, pico de demanda, fila virtual

Em cada deep dive, cubra: modelo de dados e acesso, escala (onde particionar? hotspots?), consistência e falhas (o que acontece se X cair? retry? idempotência?). Não gaste 10 minutos explicando um algoritmo de hash que ninguém pediu.

A estrutura de um bom deep dive

Para cada ponto que você aprofundar, siga este roteiro de quatro partes:

  1. O problema, com número: "temos 300 mil leituras de feed por segundo; montar o feed na hora exige consultar centenas de autores por leitura."
  2. Duas ou três opções: "posso montar na leitura (pull), pré-computar na escrita (push), ou um híbrido."
  3. Trade-offs de cada uma, ligados aos requisitos: "pull é simples e barato na escrita, mas a leitura fica lenta; push dá leitura O(1), mas um post de celebridade gera milhões de escritas."
  4. Decisão e consequências: "como a leitura precisa ser < 200 ms, vou de push, com pull só para contas com mais de 100 mil seguidores. O custo é ter dois caminhos de código."

Esse padrão (problema → opções → trade-offs → decisão) é exatamente o "sinal de profundidade" que a rubrica procura.

Checklist de falhas

Para cada componente do desenho, pergunte a si mesmo:

  • Se ele cair, o que para de funcionar? Existe réplica? Quanto tempo leva o failover?
  • Se ele ficar lento (pior que cair), quem espera por ele? Há timeout? Circuit breaker?
  • Se uma mensagem for entregue duas vezes, o resultado continua certo? (idempotência)
  • Se uma mensagem se perder, alguém percebe? (retry, reconciliação)
  • Se o tráfego vier 10× maior num minuto, o que satura primeiro?

Quando você travar

  • Diga o que está pensando: "estou em dúvida entre X e Y por causa de Z". A pessoa entrevistadora não pode ajudar com o que não ouve.
  • Volte aos requisitos: quase sempre a decisão sai deles ("priorizamos disponibilidade, então…").
  • Escolha o simples e siga em frente, anotando o ponto para revisitar. Ficar 5 minutos parada custa mais que uma decisão subótima e explícita.

Passo 4: fechamento

Nos minutos finais:

  • Identifique gargalos e melhorias. Nenhum design é perfeito, e dizer onde o seu quebra mostra maturidade.
  • Recapitule o design em 30 segundos.
  • Casos de erro: servidor cai, rede particiona, mensagem perdida.
  • Operação: métricas, logs, alertas, deploy (canary, rollback).
  • Próxima escala: o que muda de 1 milhão para 10 milhões de usuários?

O que fazer e o que evitar

Faça
  • Pergunte e confirme premissas.
  • Pense em voz alta.
  • Proponha mais de uma abordagem e compare.
  • Use números para decidir.
  • Comece simples e evolua.
  • Ouça as dicas: são presentes.
  • Gerencie o tempo e não fique presa num detalhe.
Evite
  • Chegar sem ter estudado os problemas clássicos.
  • Desenhar antes de entender o problema.
  • Ficar em silêncio pensando.
  • Despejar nomes de tecnologia sem dizer o porquê ("usei Kafka porque sim").
  • Achar que acabou quando o desenho ficou pronto.
  • Defender uma escolha ruim por teimosia.
  • Entrar em detalhes de um componente no passo 2.

Template para praticar

1. REQUISITOS (5 min)
   Funcionais: ...
   Não funcionais: escala | latência | disponibilidade × consistência | durabilidade
   Fora do escopo: ...
2. ESTIMATIVAS (2–5 min, só o que importa)
   QPS leitura/escrita (pico) | armazenamento | banda
3. API (3 min)
4. MODELO DE DADOS (3 min): entidades, chaves, qual banco e por quê
5. ALTO NÍVEL (10 min): desenhar e percorrer os fluxos
6. DEEP DIVES (15 min): 2–3 componentes críticos; escala, consistência, falhas
7. FECHAMENTO (3 min): gargalos, monitoramento, evolução

Simulação: os primeiros 5 minutos de "projete o Instagram"

Projete o Instagram.

Legal. O Instagram é grande, então quero focar no núcleo. Posso assumir que o essencial é: postar fotos com legenda, seguir pessoas e ver um feed com as fotos de quem sigo? Stories, Reels, DMs e busca ficariam de fora.

Sim, foque nisso. Adicione curtidas também.

Certo. Qual escala devo considerar? Algo como 500 milhões de DAU?

Pode ser.

E o feed é cronológico ou ranqueado?

Comece cronológico.

Para não funcionais, vou assumir: carregar o feed em menos de 200 ms, alta disponibilidade, e tolerância a consistência eventual, então tudo bem se um post aparecer para os seguidores alguns segundos depois. Mas o upload em si precisa ser durável: foto aceita não pode sumir. Faz sentido?

Faz.

Uma estimativa rápida que vai guiar o armazenamento: se 10% dos DAU postam uma foto por dia, são 50 M fotos/dia × ~2 MB = 100 TB/dia. Isso vai direto para object storage com CDN. Leituras são muito maiores que escritas, talvez 100:1, então o feed precisa ser pré-computado ou muito bem cacheado. Vou começar pela API…

Repare: a candidata cortou o escopo, confirmou premissas, transformou não funcionais em decisões ("vai para object storage", "pré-computado") e só então avançou.

O resto da entrevista do Instagram, aplicando o framework

Para ver o framework inteiro funcionando, aqui está como os outros passos poderiam ficar.

API

POST /v1/media/upload-url                    → 200 { upload_url, media_id }   # URL pré-assinada do S3
POST /v1/posts         { media_id, caption } → 201 { post_id }
POST /v1/users/{id}/follow                   → 204
POST /v1/posts/{id}/likes                    → 204   # idempotente: curtir duas vezes = uma curtida
GET  /v1/feed?cursor=…&limit=20             → 200 { posts[], next_cursor }

O upload vai direto do app para o S3 por uma URL pré-assinada: os bytes da foto nunca passam pelos servidores de aplicação, que só lidam com metadados.

Modelo de dados

EntidadeOndeChave / acesso
usersPostgrespor id
follows (seguidor, seguido)Postgres ou Cassandradois índices: "quem eu sigo" e "quem me segue"
postsCassandrapartição por author_id, ordenado por post_id (que já embute o tempo; veja IDs únicos)
likesCassandra + contador em Redis(post_id, user_id) único; contagem agregada à parte
feedRedislista dos últimos ~500 post_ids por usuário
fotosS3 + CDNpor media_id, em vários tamanhos

Alto nível

Deep dives que a candidata escolheria

  1. Fanout e celebridades: híbrido push/pull, como no capítulo de News feed.
  2. Contagem de curtidas: um post viral recebe milhares de curtidas por segundo na mesma linha. Gravar cada curtida como linha única (garante idempotência) e manter o contador agregado no Redis, persistido em lotes.
  3. Mídia: pipeline assíncrono de redimensionamento, vários tamanhos por tela, CDN com URLs imutáveis.

Fechamento

"O principal risco é o Redis de feeds: se perdê-lo, os feeds podem ser reconstruídos a partir dos posts, mas isso é caro, então ele roda replicado. Monitoraria latência p99 do feed, atraso do fanout (tempo entre postar e aparecer) e tamanho da fila. Com 10× de escala, o grafo de follows vira o próximo gargalo e precisaria de cache dedicado."
