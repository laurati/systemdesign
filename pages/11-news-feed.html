Projete um news feed

Facebook, Instagram, X/Twitter, LinkedIn: o feed é a lista de posts das pessoas que você segue. O coração do problema é uma decisão: pré-computar o feed na escrita ou montá-lo na leitura?

Ao final você saberá:

  • Desenhar os fluxos de publicação e de leitura do feed.
  • Comparar fanout on write, fanout on read e o modelo híbrido.
  • Resolver o problema da celebridade.
  • Organizar o cache em camadas e implementar o fanout híbrido em Go.

Conceitos deste capítulo

ConceitoDefinição
News feedLista, atualizada continuamente, dos posts das pessoas e páginas que o usuário segue.
FanoutDistribuir um post para todos os seguidores do autor.
Fanout on write (push)Fazer o fanout no momento da publicação, gravando o post no feed pré-computado de cada seguidor.
Fanout on read (pull)Montar o feed só quando o usuário o abre, buscando os posts recentes de quem ele segue.
Problema da celebridadeContas com milhões de seguidores tornam o push caro e lento demais.
Grafo socialAs relações de quem segue quem, normalmente guardadas como arestas (seguidor, seguido).
HidrataçãoTransformar uma lista de IDs em objetos completos (texto, autor, foto, contadores) para exibir.
Paginação por cursorPedir a próxima página a partir do último item visto, em vez de um número de página.

5.000.

10 milhões de DAU.

Mídia?

Imagens e vídeos.

Estimativas

Premissas: 10 M DAU; cada usuário publica 1 post a cada 5 dias (2 M posts/dia); abre o feed 10 vezes por dia; média de 200 seguidores.

  • Publicações: 2 M / 105 ≈ 20/s (pico ~60/s). Baixo.
  • Leituras de feed: 10 M × 10 / 105 = 1.000/s (pico ~3.000/s). Cada leitura traz 20 posts.
  • Escritas de fanout (push): 2 M posts × 200 seguidores = 400 M inserções por dia ≈ 4.000/s. A operação "barata" de publicar se multiplica por 200 no backend.
  • Memória do feed cache: 10 M usuários × 500 post_ids × 8 bytes = 40 GB brutos; com overhead das estruturas do Redis, ~100 GB. Alguns nós.

O que isso implica: a leitura é 50× mais frequente que a publicação e precisa ser rápida, o que favorece pré-computar (push). Mas o custo do push é proporcional ao número de seguidores, e esse número tem uma distribuição muito desigual: a média é 200, mas algumas contas têm dezenas de milhões. É daí que vem o problema central do capítulo.

APIs

POST /v1/me/feed     { content, media_ids[], auth_token }      → publica
GET  /v1/me/feed?cursor=<post_id>&limit=20                    → lê o feed

Use paginação por cursor (o último post_id visto), não por offset: com posts novos entrando no topo, o offset duplica ou pula itens e fica lento em páginas profundas.

Deep dive: fanout

Fanout on write (push)Fanout on read (pull)
QuandoNa publicação, o post_id é escrito no feed de cada seguidorNa leitura, buscam-se os posts recentes de cada pessoa seguida e mescla-se
LeituraRápida: o feed já está prontoLenta: N consultas + merge

A resposta: modelo híbrido Push para a maioria (usuários com poucos seguidores, leitura rápida); pull para celebridades: os posts delas não são distribuídos e são buscados e mesclados na hora da leitura. Usar consistent hashing nos caches distribui a carga das leituras de celebridades. Bônus: só fazer fanout para seguidores ativos recentemente.
go/feed/feed.go: fanout híbrido (push + pull para celebridades)
// Package feed implementa um news feed com modelo HÍBRIDO de fanout:
//
//   - Fanout on write (push): ao publicar, o post_id é inserido no cache de
//     feed de cada seguidor. Leitura rapidíssima; escrita cara para quem tem
//     milhões de seguidores (o "problema da celebridade").
//   - Fanout on read (pull): o feed é montado na hora da leitura buscando os
//     posts de quem a pessoa segue. Escrita barata; leitura lenta.
//
// Híbrido: push para usuários comuns, pull para celebridades (acima de um limiar).
package feed

import (
	"slices"
	"sync"
)

type Post struct {
	ID       int64 // ID ordenável por tempo (Snowflake) — dispensa campo de timestamp
	AuthorID string
	Text     string
}

type Service struct {
	mu                 sync.RWMutex
	CelebrityThreshold int
	MaxFeedSize        int // limita o cache de feed por usuário (ex.: 500 ids)

	followers map[string]map[string]bool // autor -> seguidores
	following map[string]map[string]bool // usuário -> quem segue
	posts     map[int64]Post             // "post store"
	byAuthor  map[string][]int64         // posts de cada autor (para o pull)
	feedCache map[string][]int64         // feed pré-computado (para o push)
}

func NewService(celebrityThreshold, maxFeed int) *Service {
	return &Service{
		CelebrityThreshold: celebrityThreshold, MaxFeedSize: maxFeed,
		followers: map[string]map[string]bool{}, following: map[string]map[string]bool{},
		posts: map[int64]Post{}, byAuthor: map[string][]int64{}, feedCache: map[string][]int64{},
	}
}

func (s *Service) Follow(user, author string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.followers[author] == nil {
		s.followers[author] = map[string]bool{}
	}
	if s.following[user] == nil {
		s.following[user] = map[string]bool{}
	}
	s.followers[author][user] = true
	s.following[user][author] = true
}

func (s *Service) isCelebrity(author string) bool {
	return len(s.followers[author]) >= s.CelebrityThreshold
}

// Publish grava o post e faz fanout on write se o autor não é celebridade.
// Em produção o fanout é assíncrono: Publish enfileira e workers escrevem nos caches.
func (s *Service) Publish(p Post) (fanout int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.posts[p.ID] = p
	s.byAuthor[p.AuthorID] = append(s.byAuthor[p.AuthorID], p.ID)
	if s.isCelebrity(p.AuthorID) {
		return 0 // seguidores vão "puxar" na leitura
	}
	for f := range s.followers[p.AuthorID] {
		feed := append([]int64{p.ID}, s.feedCache[f]...)
		if len(feed) > s.MaxFeedSize {
			feed = feed[:s.MaxFeedSize]
		}
		s.feedCache[f] = feed
		fanout++
	}
	return fanout
}

// Feed mescla o cache (push) com os posts recentes das celebridades seguidas (pull).
func (s *Service) Feed(user string, limit int) []Post {
	s.mu.RLock()
	defer s.mu.RUnlock()
	ids := slices.Clone(s.feedCache[user])
	for author := range s.following[user] {
		if s.isCelebrity(author) {
			ids = append(ids, s.byAuthor[author]...)
		}
	}
	slices.Sort(ids)
	ids = slices.Compact(ids)
	slices.Reverse(ids) // mais recentes primeiro
	out := make([]Post, 0, limit)
	for _, id := range ids {
		if len(out) == limit {
			break
		}
		out = append(out, s.posts[id]) // "hydration": id -> conteúdo completo
	}
	return out
}

Onde colocar o limiar de celebridade

Pense no custo de cada lado. Um autor com F seguidores custa F escritas por post no modelo push. No modelo pull, cada seguidor que abre o feed faz uma leitura extra dos posts recentes desse autor. Se o autor tem 50 milhões de seguidores e posta 5 vezes por dia, o push custa 250 milhões de escritas por dia só para ele, e cada post leva minutos para chegar a todos. Com pull, o custo é uma leitura (muito cacheável, porque é o mesmo dado para todos) por abertura de feed.

Limiares típicos ficam entre 10 mil e 1 milhão de seguidores. O valor exato importa menos que três ideias: (1) o limiar é configurável; (2) o pull de celebridades é barato porque "posts recentes da celebridade X" é uma única chave de cache lida por todos; (3) cada usuário segue poucas celebridades (dezenas), então o merge na leitura continua pequeno.

Montando o feed híbrido na leitura

  1. Lê o feed pré-computado do usuário: uma lista de post_ids ordenada (vindo do push).
  2. Lê a lista de celebridades que ele segue (poucas) e, para cada uma, os post_ids recentes (do cache "posts por autor").
  3. Faz o merge das listas, que já estão ordenadas por post_id (e o post_id é ordenado por tempo, por ser um Snowflake): é um k-way merge com um heap, pegando os 20 maiores IDs menores que o cursor.
  4. Hidrata os 20 IDs (conteúdo, autor, contadores) com MGET nos caches.
  5. Filtra o que não deve aparecer (post apagado, autor bloqueado depois do fanout) e devolve, com next_cursor = menor post_id da página.

Como o cursor é um post_id e todas as fontes são ordenadas pelo mesmo ID, a paginação funciona igual para posts vindos do push e do pull.

Como o fanout service trabalha

  1. Busca os IDs dos seguidores no graph DB (ou numa tabela follows com índice).
  2. Filtra pelas configurações do usuário (mutados, bloqueados, feed restrito).
  3. Publica na fila: (post_id, lista de seguidores) em lotes.
  4. Workers inserem post_id no feed cache de cada seguidor: Redis LPUSH + LTRIM para manter só os N mais recentes (por exemplo, 500).

O feed cache guarda só IDs (<post_id, user_id>): guardar o post completo multiplicaria a memória pelo número de seguidores. A maioria só rola os posts mais recentes, então o miss em posts antigos é raro.

Fluxo de leitura do feed

A hidratação (transformar IDs em posts completos com autor, contadores e mídia) é feita em lote (MGET) a partir dos caches de posts e usuários. Imagens e vídeos vêm da CDN.

Cache em camadas

CamadaConteúdo
News feedIDs dos posts do feed de cada usuário
ConteúdoDados de cada post; posts populares num cache "quente" separado
Social graphSeguidores e seguidos
AçãoSe o usuário curtiu, respondeu, compartilhou
ContadoresCurtidas, respostas, seguidores (contadores em Redis, persistidos em lote)

Modelo de dados e armazenamento

  • Posts: post_id (Snowflake, ordenável por tempo), author_id, content, media_urls, created_at. Volume alto, acesso por id e por autor: Cassandra/DynamoDB, ou MySQL sharded por author_id.
  • Follows: (follower_id, followee_id) com índices nas duas direções, num relacional sharded ou num graph store (TAO no Facebook).
  • Mídia: S3 + CDN.

Casos que quebram o feed (e como tratar)

Usuário começa a seguir alguémO feed pré-computado não tem os posts antigos dessa pessoaBackfill assíncrono: inserir os últimos N posts dela no feed do novo seguidor (ou aceitar que só os novos apareçam)
Usuário deixa de seguirOs posts já estão no feed deleFiltrar na leitura (checar se ainda segue o autor) e limpar em segundo plano
Post apagadoO ID está em milhares de feedsNão limpar cada feed: marcar o post como apagado e filtrar na hidratação
Usuário volta após 6 mesesFeed expirou do cache (ou nunca foi computado, se o fanout pula inativos)Reconstruir sob demanda com pull na primeira abertura e repopular o cache

Como funciona um feed ranqueado

Se o entrevistador mudar o requisito para "ordenado por relevância", a arquitetura de armazenamento quase não muda; o que entra é um pipeline na leitura:

  1. Geração de candidatos: os ~500 a 1.000 posts recentes vindos do push e do pull (exatamente o que já temos).
  2. Features: para cada candidato, dados como afinidade do leitor com o autor (interações recentes), tipo de mídia, idade do post, engajamento até agora. Ficam num feature store de baixa latência.
  3. Pontuação: um modelo de ML estima a probabilidade de curtir, comentar ou passar mais tempo, e combina numa nota.
  4. Regras finais: diversidade (não mostrar 5 posts seguidos do mesmo autor), remoção do que já foi visto, conteúdo patrocinado.

A paginação muda: com ranking, "o próximo" não é mais "o de ID menor". O comum é ranquear um lote, guardar o resultado numa sessão de feed com TTL curto e paginar sobre ele.

Para o fechamento

  • Ranking: o feed ranqueado busca ~500 candidatos (push + pull) e um modelo de ML pontua por afinidade, tipo de conteúdo e recência. O ranking acontece na leitura.
  • Edição e remoção: como o cache guarda IDs, basta atualizar ou marcar o post; na hidratação, posts removidos são filtrados.
  • Escala do banco: réplicas de leitura, sharding, e a camada web stateless.
  • Monitoramento: QPS em horários de pico, latência de atualização do feed.

Simulação de entrevista

Uma cantora com 80 milhões de seguidores posta. O que acontece no seu sistema?

Ela está acima do limiar de celebridade (por exemplo, 100 mil seguidores), então o post não é distribuído. Ele é gravado no post store e aparece num cache "posts recentes por autor". Quando um fã abre o feed, o serviço pega o feed pré-computado dele (push) e mescla com os posts recentes das poucas celebridades que ele segue (pull), ordenando por post_id. Isso troca 80 milhões de escritas por uma leitura extra, barata e muito cacheada, por fã.

Mas 80 milhões de fãs vão ler o mesmo post ao mesmo tempo: hot key.

Sim, o post dessa celebridade vira a chave mais quente do cache. Eu replicaria esse objeto em vários nós de cache (a chave com sufixo aleatório na leitura) e manteria um cache local in-process nos servidores de feed com TTL de poucos segundos. Os contadores de curtidas desse post também são quentes: acumulo incrementos em memória e gravo em lote, e mostro números aproximados.

E um usuário comum com 3 mil seguidores?

Push assíncrono: o post entra na fila e os workers fazem LPUSH/LTRIM nos feeds de 3 mil seguidores em alguns lotes. Se esses seguidores não abrem o app há 30 dias, pulo o fanout para eles e o feed deles é montado por pull quando voltarem.

Qual latência entre postar e aparecer?

Para usuários comuns, a latência da fila mais a escrita no cache, normalmente abaixo de alguns segundos. Monitoro a idade das mensagens na fila de fanout como SLI.

Quiz

Por que o feed cache guarda só IDs?
O conteúdo fica em um único lugar (post cache); o feed referencia.
Principal problema do fanout on write puro?
É o problema da celebridade; daí o modelo híbrido.
Melhor paginação para um feed que recebe itens novos constantemente?
Estável com inserções no topo e eficiente em qualquer profundidade.
