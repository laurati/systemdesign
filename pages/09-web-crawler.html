Projete um web crawler

Baixar bilhões de páginas, extrair links e repetir, sem derrubar sites alheios, sem baixar a mesma coisa duas vezes e sem cair em armadilhas.

Ao final você saberá:

  • Desenhar os componentes de um crawler e o fluxo entre eles.
  • Projetar o URL frontier com prioridade e politeness.
  • Deduplicar URLs e conteúdo em escala (Bloom filter, checksums).
  • Lidar com robots.txt, armadilhas, falhas e escala distribuída.

Para que serve um crawler

  • Indexação de buscadores (Googlebot).
  • Arquivamento (Internet Archive).
  • Mineração de dados (análise de mercado, preços).
  • Monitoramento (violação de direitos autorais).
  • Hoje, também coleta de dados para treinar LLMs.

Requisitos

Qual o propósito?

Indexação para um buscador.

Quantas páginas por mês?

1 bilhão.

Que tipo de conteúdo? Só HTML?

Só HTML.

Considerar páginas novas e editadas?

Sim.

Guardar as páginas?

Sim, por até 5 anos.

Conteúdo duplicado?

Ignorar.

Características desejadas: escalabilidade (paralelismo), robustez (HTML malformado, servidores que não respondem, armadilhas), politeness (não sobrecarregar sites) e extensibilidade (novos tipos de conteúdo no futuro).

Estimativas

  • 1 bilhão de páginas/mês ÷ (30 × 105 s) ≈ 400 páginas/s; pico ~800/s.
  • Página média de 500 KB, então 1 bi × 500 KB = 500 TB/mês, e em 5 anos 30 PB.
  • Banda de download: 400 páginas/s × 500 KB = 200 MB/s ≈ 1,6 Gbps em média, ~3 Gbps no pico.
  • Conexões simultâneas (Lei de Little): se cada download leva ~1 s em média (servidores lentos, DNS, TLS), há ~400 downloads em andamento a qualquer momento; no pico, ~800.

O que isso implica: a vazão em si é modesta (algumas dezenas de máquinas). Os desafios reais são outros: armazenar 30 PB (compressão e object storage), não baixar a mesma coisa duas vezes (dedup em bilhões de URLs) e, principalmente, distribuir os downloads entre milhões de sites diferentes sem sobrecarregar nenhum.

Politeness também é uma conta Se a regra é no máximo 1 requisição por segundo para cada host e queremos 400 páginas/s, precisamos estar baixando de pelo menos 400 hosts diferentes ao mesmo tempo. Na prática, muitos hosts pedem intervalos maiores (Crawl-delay), então o frontier precisa manter dezenas de milhares de hosts "prontos" em paralelo. É por isso que a estrutura com uma fila por host é necessária, e não só uma otimização.

A vida de uma URL

Seguir uma URL do começo ao fim ajuda a ver por que cada componente existe:

  1. A URL https://Exemplo.com/blog/../noticias?utm_source=x#topo é extraída de uma página.
  2. Normalização: vira https://exemplo.com/noticias (host em minúsculas, .. resolvido, parâmetros de rastreamento e fragmento removidos). Sem isso, a mesma página aparece com dezenas de URLs diferentes.
  3. Filtro: não é .jpg, .zip nem um domínio bloqueado.
  4. "URL já vista?": o Bloom filter diz que não. A URL é gravada no URL storage e entra no frontier.
  5. Frontier: o prioritizer dá nota alta (o site é popular), a URL entra numa front queue de alta prioridade e depois na back queue do host exemplo.com.
  6. Quando o host está liberado (passou o intervalo desde o último download), um worker pega a URL, consulta o robots.txt em cache (o caminho /noticias é permitido) e o DNS em cache.
  7. Download com timeout. A resposta é HTML de 400 KB.
  8. "Conteúdo já visto?": o hash não bate com nenhum anterior. O HTML é comprimido e armazenado.
  9. O parser extrai 120 links, e cada um recomeça no passo 1. O host exemplo.com ganha um novo horário livre em, digamos, 1 s.

O fluxo numerado

DFS × BFS

A web é um grafo direcionado. DFS mergulha fundo demais. BFS (fila FIFO) é o padrão, mas tem dois problemas: (1) a maioria dos links de uma página aponta para o mesmo host, então a BFS pura martela um servidor (impolido); (2) não há prioridade, e nem toda página tem a mesma importância. O URL frontier resolve os dois.

Deep dive: o URL frontier

Politeness

Uma única conexão por host de cada vez, com um intervalo entre downloads. Implementação: uma fila por host (back queues), e cada worker consome de uma fila de cada vez. Um mapa host → fila decide onde cada URL entra.

Prioridade

Um prioritizer pontua as URLs (PageRank, tráfego, frequência de atualização) e as coloca em front queues por prioridade; um seletor escolhe as filas de maior prioridade com mais probabilidade.

Como as duas camadas de filas trabalham juntas

  • As front queues respondem "o que é mais importante?". Há poucas (uma por nível de prioridade).
  • As back queues respondem "de quem posso baixar agora?". Cada uma contém URLs de um único host. Uma regra prática do design original (Mercator) é ter cerca de 3 back queues por thread de download, para sempre haver alguma liberada.
  • Um heap guarda, para cada back queue, o próximo instante em que o host pode ser acessado. O worker tira o topo do heap (o host liberado há mais tempo), baixa uma URL e devolve o host ao heap com horário = agora + intervalo.
  • Quando uma back queue esvazia, o seletor puxa URLs das front queues (com viés para as de alta prioridade) até encontrar uma de um host que ainda não tem fila, e cria a fila desse host.

O intervalo por host pode ser fixo (1 s), vir do Crawl-delay do robots.txt, ou ser adaptativo: um múltiplo do tempo que o último download levou (se o servidor demorou 2 s para responder, espere 10× isso). Servidores lentos recebem menos carga automaticamente.

Freshness e armazenamento

  • Recrawl com base no histórico de mudanças da página; páginas importantes com mais frequência.
  • O frontier tem centenas de milhões de URLs: não cabe em memória. A maior parte fica em disco, com buffers em memória para enfileirar e desenfileirar e escrita em lote.
go/crawler/frontier.go: prioridade por host, politeness com min-heap e dedup
// Package crawler implementa o "URL frontier" de um web crawler:
// a estrutura que decide QUAL URL baixar a seguir respeitando
//
//   - prioridade (páginas importantes primeiro — front queues);
//   - politeness (no máximo 1 requisição por host a cada `delay` — back queues);
//   - deduplicação (não baixar a mesma URL duas vezes).
package crawler

import (
	"container/heap"
	"net/url"
	"sync"
	"time"
)

type Frontier struct {
	mu      sync.Mutex
	delay   time.Duration
	now     func() time.Time
	seen    map[string]bool     // em produção: Bloom filter ou store de hashes
	perHost map[string][]queued // back queue por host (FIFO por prioridade)
	ready   hostHeap            // min-heap: próximo instante em que cada host pode ser visitado
	inHeap  map[string]bool
}

type queued struct {
	url      string
	priority int // maior = mais importante (PageRank, frequência de atualização…)
}

func NewFrontier(delay time.Duration, now func() time.Time) *Frontier {
	if now == nil {
		now = time.Now
	}
	return &Frontier{delay: delay, now: now, seen: map[string]bool{}, perHost: map[string][]queued{}, inHeap: map[string]bool{}}
}

// Add normaliza e enfileira a URL se ainda não foi vista.
func (f *Frontier) Add(raw string, priority int) bool {
	u, err := url.Parse(raw)
	if err != nil || u.Host == "" || (u.Scheme != "http" && u.Scheme != "https") {
		return false
	}
	u.Fragment = "" // #secao aponta para a mesma página
	norm := u.String()

	f.mu.Lock()
	defer f.mu.Unlock()
	if f.seen[norm] {
		return false
	}
	f.seen[norm] = true

	q := append(f.perHost[u.Host], queued{norm, priority})
	// Inserção ordenada por prioridade dentro do host (estável).
	for i := len(q) - 1; i > 0 && q[i].priority > q[i-1].priority; i-- {
		q[i], q[i-1] = q[i-1], q[i]
	}
	f.perHost[u.Host] = q
	if !f.inHeap[u.Host] {
		heap.Push(&f.ready, hostSlot{host: u.Host, at: f.now()})
		f.inHeap[u.Host] = true
	}
	return true
}

// Next devolve a próxima URL que pode ser baixada agora, ou "" se nenhum
// host está liberado (o worker deve esperar).
func (f *Frontier) Next() string {
	f.mu.Lock()
	defer f.mu.Unlock()
	if f.ready.Len() == 0 || f.ready[0].at.After(f.now()) {
		return ""
	}
	slot := heap.Pop(&f.ready).(hostSlot)
	q := f.perHost[slot.host]
	next := q[0]
	f.perHost[slot.host] = q[1:]
	if len(q) > 1 {
		heap.Push(&f.ready, hostSlot{host: slot.host, at: f.now().Add(f.delay)})
	} else {
		delete(f.inHeap, slot.host)
	}
	return next.url
}

type hostSlot struct {
	host string
	at   time.Time
}

type hostHeap []hostSlot

func (h hostHeap) Len() int           { return len(h) }
func (h hostHeap) Less(i, j int) bool { return h[i].at.Before(h[j].at) }
func (h hostHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *hostHeap) Push(x any)        { *h = append(*h, x.(hostSlot)) }
func (h *hostHeap) Pop() any {
	old := *h
	x := old[len(old)-1]
	*h = old[:len(old)-1]
	return x
}

Recrawl: quando visitar de novo

Uma página de notícias muda a cada minuto; uma página "sobre nós" muda uma vez por ano. Revisitar tudo na mesma frequência desperdiça banda com as estáticas e deixa as dinâmicas desatualizadas. A abordagem comum é adaptativa: a cada visita, compare com a versão anterior; se mudou, encurte o intervalo (por exemplo, pela metade); se não mudou, aumente-o (por exemplo, 1,5×), dentro de limites mínimo e máximo. Páginas importantes recebem um teto menor.

Para economizar banda, use GET condicional: envie If-Modified-Since ou If-None-Match (com o ETag da última versão). Se a página não mudou, o servidor responde 304 Not Modified sem corpo.

Deep dive: o downloader

  • robots.txt (Robots Exclusion Protocol): baixe-o por domínio, cacheie e respeite Disallow e Crawl-delay.
  • Crawl distribuído: muitos servidores, cada um com muitas threads; particione as URLs por host (hash do host → worker), para que a politeness seja local.
  • Cache de DNS atualizado por cron.
  • Localidade: crawlers perto dos sites (por região).
  • Timeouts curtos: servidores lentos não podem prender workers.

Um robots.txt real

User-agent: *
Disallow: /admin/
Disallow: /busca
Crawl-delay: 5

User-agent: MeuCrawler
Disallow: /

Sitemap: https://exemplo.com/sitemap.xml

Para o crawler genérico (*): não visitar /admin/ nem /busca e esperar 5 s entre requisições. O crawler chamado MeuCrawler está proibido em todo o site. O Sitemap é um presente: lista as URLs que o dono quer indexadas, muitas vezes com data da última modificação, o que ajuda no recrawl. Cacheie o robots.txt por host (por exemplo, por 24 h) e, se ele der erro 5xx, seja conservador e não rastreie o host por um tempo.

Downloads assíncronos

Com centenas de downloads simultâneos que passam a maior parte do tempo esperando a rede, uma thread por download desperdiça memória. Crawlers modernos usam I/O assíncrono (event loop ou goroutines, que são baratas) e cada máquina mantém milhares de conexões abertas.

Extensibilidade

Robustez

  • Consistent hashing para distribuir carga entre downloaders e permitir adicionar ou remover servidores.
  • Salvar o estado do crawl (frontier, URLs vistas) periodicamente para retomar após falhas.
  • Tratamento de exceções: um erro não pode derrubar o sistema; registre e siga.
  • Validação de dados para evitar erros de parsing.

Deduplicação

URLs vistas: 1 bilhão/mês e dezenas de bilhões no total. Um set exato custaria terabytes. Um Bloom filter com 1% de falso positivo usa ~9,6 bits por URL (~1,2 GB por bilhão). O falso positivo significa só "deixei de baixar 1% de URLs novas", o que é aceitável.

go/bloom/bloom.go (trecho): dimensionamento
// New dimensiona o filtro para n itens com taxa de falso positivo p:
//
//	m = -n·ln(p) / (ln 2)²     k = (m/n)·ln 2
//
// Ex.: 1 bilhão de URLs com p=1% ≈ 9,6 bits/item ≈ 1,2 GB — cabe em memória.
func New(n int, p float64) *Filter {
	m := uint64(math.Ceil(-float64(n) * math.Log(p) / (math.Ln2 * math.Ln2)))
	k := uint64(math.Round(float64(m) / float64(n) * math.Ln2))
	return &Filter{bits: make([]uint64, (m+63)/64), m: m, k: max(k, 1)}
}

Conteúdo duplicado: comparar páginas caractere a caractere é lento. Compare hashes (checksum do conteúdo). Para quase duplicatas (mesma página com data diferente), use SimHash/MinHash.

Como o SimHash encontra quase duplicatas

Um hash comum (SHA-256) muda completamente se um único caractere mudar, então não serve para "quase igual". O SimHash faz o contrário: textos parecidos geram hashes parecidos.

  1. Divida o texto em pedaços (palavras ou grupos de 3 palavras) e calcule o hash de 64 bits de cada pedaço.
  2. Mantenha 64 contadores. Para cada pedaço, em cada posição de bit: se o bit for 1, some 1 ao contador; se for 0, subtraia 1.
  3. O SimHash final tem bit 1 onde o contador ficou positivo e 0 onde ficou negativo.

Se duas páginas compartilham 95% das palavras, quase todos os contadores apontam para o mesmo lado, e os SimHashes diferem em poucos bits. A regra usada pelo Google na indexação web foi considerar quase duplicatas páginas cujos SimHashes de 64 bits diferem em até 3 bits. Para não comparar cada página com bilhões de outras, os hashes são indexados em tabelas por blocos de bits (se diferem em até 3 de 64 bits, pelo menos um bloco de 16 bits é idêntico).

Armazenando 30 PB

  • Compressão: HTML comprime muito bem (texto repetitivo, ~5–10×), o que reduz 30 PB para alguns PB.
  • Não um objeto por página: bilhões de objetos pequenos são caros em object storage (custo por requisição, metadados). O padrão é juntar milhares de páginas em arquivos grandes (como o formato WARC do Internet Archive) e manter um índice URL → (arquivo, offset, tamanho).
  • Camadas: a versão mais recente de cada página em armazenamento "quente"; versões antigas numa classe fria e barata.

Conteúdo problemático

  • Spider traps: URLs infinitas, como site.com/foo/bar/foo/bar/… ou calendários com "próximo mês" para sempre. Limite o tamanho da URL e a profundidade por host; detecte padrões manualmente e mantenha uma blocklist.
  • Dados sem valor: anúncios, código, spam: filtre.
  • Renderização de JavaScript: SPAs geram links dinamicamente; renderize num headless browser (caro, então use só onde necessário).

Simulação de entrevista

Seu crawler está fazendo 500 requisições/s em um único site pequeno, e o dono reclamou. O que aconteceu e como evitar?

É falta de politeness. Na BFS pura, uma página de um site traz dezenas de links do mesmo site, e vários workers os baixam em paralelo. A correção estrutural é o frontier com uma back queue por host: todas as URLs de um host vão para a mesma fila, só um worker consome dela de cada vez, e há um intervalo mínimo entre requisições (o Crawl-delay do robots.txt ou um padrão de 1 s). Um heap ordenado pelo "próximo horário permitido" de cada host diz aos workers qual fila está liberada.

Com milhões de hosts, como você distribui isso entre 100 máquinas?

Particiono por host: hash(host) com consistent hashing escolhe a máquina responsável. Assim, a politeness de um host fica inteiramente numa máquina e não preciso de coordenação global. Quando o link extractor encontra uma URL de outro host, ela é enviada para a máquina dona, via fila particionada pela mesma chave, como um tópico Kafka com chave = host.

E como evitar baixar a mesma URL duas vezes entre as máquinas?

Como cada host tem um único dono, o "URL seen?" também pode ser local por partição: um Bloom filter por máquina para os hosts que ela possui, mais um store persistente de URLs para checkpoints. Normalizo a URL antes (minúsculas no host, remoção de fragmentos e de parâmetros de tracking) para que variações não pareçam URLs diferentes.
